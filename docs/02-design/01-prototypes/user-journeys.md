## Epic 1: Onboarding & Personalization

### ONB-0 — สมัครสมาชิก / เข้าสู่ระบบ / ลืมรหัสผ่าน / ออกจากระบบ (REQ-14, REQ-15, REQ-16, REQ-17)

```mermaid
flowchart TD
    A["เปิดเว็บแอป (apps/web/client — ONB-0 เป็น web-only เท่านั้น)"] --> B{มีบัญชีผู้ใช้อยู่แล้วหรือไม่?}
    B -- ยังไม่มีบัญชี --> C["เลือกวิธีสมัครสมาชิก: email/password, Google, หรือ Apple"]
    C --> D[สร้างบัญชีผู้ใช้ userId ใหม่]
    D --> E[ไปขั้นตอนกรอกข้อมูลส่วนตัว ONB-1]
    B -- มีบัญชีอยู่แล้ว --> F["เลือกวิธีเข้าสู่ระบบ: วิธีเดียวกับที่สมัครไว้"]
    F --> G{เข้าสู่ระบบสำเร็จ?}
    G -- สำเร็จ --> H["จดจำสถานะ login ไว้ (session persistence)"]
    H --> I["เข้าแอปต่อ (Daily Dashboard ถ้าผ่าน onboarding แล้ว หรือกลับไปทำ ONB-1 ต่อถ้ายังไม่เคยผ่าน)"]
    G -- ลืมรหัสผ่าน (เฉพาะ email/password) --> J[ขอรีเซ็ตรหัสผ่านผ่านอีเมลที่ลงทะเบียนไว้]
    J --> F
    I --> K[ผู้ใช้กดออกจากระบบจากหน้าโปรไฟล์ เมื่อไหร่ก็ได้]
    K --> L[ล้าง session ทันที]
    L --> B
```

**คำอธิบายตามลำดับ diagram:**

1. ผู้ใช้เปิด**เว็บแอป** (ครั้งแรก หรือหลังออกจากระบบ/session หมดอายุ) ระบบตรวจสอบว่ามีบัญชีผู้ใช้อยู่แล้วหรือไม่
   — ONB-0 เป็น **web-only**: หน้าจอสมัคร/เข้าสู่ระบบ/ลืมรหัสผ่าน/ออกจากระบบทั้งหมดมีอยู่เฉพาะที่เว็บแอป
   (`apps/web/client/`) เท่านั้น แอปมือถือ (companion app ของ [INT-2](#int-2--ซิงค์ตาชั่งอัจฉริยะ-req-12)/
   [INT-3](#int-3--ซิงค์ข้อมูล-wearable-req-13)) ไม่มีหน้าจอเหล่านี้เลย ตาม
   [decision ที่ยืนยันแล้วใน Onboarding spec](../../01-requirements/01-spec/20260823-01-onboarding-personalization.md#ข้อสมมติฐานการตัดสินใจที่ยืนยันแล้ว)
   (REQ-14, REQ-15)
2. **กรณียังไม่มีบัญชี**: ผู้ใช้เลือกวิธีสมัครสมาชิก 1 ใน 3 วิธี — email/password, Google OAuth, หรือ
   Sign in with Apple ตาม
   [decision ที่ยืนยันแล้วใน Onboarding spec](../../01-requirements/01-spec/20260823-01-onboarding-personalization.md#ข้อสมมติฐานการตัดสินใจที่ยืนยันแล้ว)
   (REQ-14)
3. ระบบสร้างบัญชีผู้ใช้ใหม่ (`userId`) ก่อนเข้าสู่ขั้นตอนกรอกข้อมูลส่วนตัวเสมอ — ห้ามเริ่ม ONB-1 ก่อนมี
   บัญชีผู้ใช้จริง (REQ-14)
4. เมื่อมีบัญชีแล้ว ระบบพาไปยังขั้นตอนกรอกข้อมูลส่วนตัว (ONB-1) (REQ-14)
5. **กรณีมีบัญชีอยู่แล้ว (ผู้ใช้เดิม)**: ผู้ใช้เลือกวิธีเข้าสู่ระบบด้วยวิธีเดียวกับที่สมัครไว้ (REQ-15)
6. ระบบตรวจสอบว่าเข้าสู่ระบบสำเร็จหรือไม่ (REQ-15)
7. **กรณีสำเร็จ**: ระบบจดจำสถานะเข้าสู่ระบบไว้ (session persistence) เพื่อไม่ต้อง login ซ้ำทุกครั้งที่เปิด
   แอป จนกว่าจะออกจากระบบเองหรือ session หมดอายุ (REQ-15)
8. ผู้ใช้เข้าแอปต่อได้ทันที — ไปยัง Daily Dashboard (REC-1) ถ้าผ่าน onboarding ครบแล้ว หรือกลับไปทำ ONB-1
   ต่อถ้ายังไม่เคยผ่าน (REQ-15)
9. **กรณีผู้ใช้ที่สมัครด้วย email/password ลืมรหัสผ่าน**: ขอรีเซ็ตรหัสผ่านผ่านอีเมลที่ลงทะเบียนไว้ได้
   (ใช้ไม่ได้กับบัญชีที่สมัครผ่าน Google/Apple เพราะไม่มีรหัสผ่านให้รีเซ็ต) แล้ววนกลับไปเข้าสู่ระบบใหม่ (REQ-16)
10. ผู้ใช้ที่เข้าสู่ระบบอยู่สามารถออกจากระบบได้ทุกเมื่อจากหน้าโปรไฟล์ (REQ-17)
11. ระบบล้าง session ที่จดจำไว้ตาม REQ-15 ทันที แล้วกลับไปหน้าจอสมัครสมาชิก/เข้าสู่ระบบเริ่มต้น (REQ-17)

- **Actor/Persona**: ทั้งผู้ใช้ใหม่ (first-time user) ที่ยังไม่มีบัญชี และผู้ใช้ประจำ (returning user) ที่
  กลับมาเปิดแอปอีกครั้ง
- **Goal**: มีบัญชีผู้ใช้ที่ปลอดภัยและเข้าถึงแอปได้ต่อเนื่อง โดยไม่ต้อง login ซ้ำทุกครั้งที่เปิดแอป
- **Trigger**: เปิดแอปครั้งแรก / เปิดแอปหลัง session หมดอายุหรือหลัง logout / ลืมรหัสผ่านระหว่าง login /
  กดออกจากระบบจากหน้าโปรไฟล์
- **Preconditions**: ไม่มี — เป็นจุดเริ่มต้นสุดของทั้งแอป เกิดขึ้นก่อน ONB-1 เสมอ
- **Success State**: ผู้ใช้มีบัญชีผู้ใช้ (`userId`) จริง และอยู่ในสถานะเข้าสู่ระบบ พร้อมเข้าถึงทุก feature
  อื่นในแอปได้ (REQ-14, REQ-15)
- **Alt/Edge Cases**:
  - ผู้ใช้ที่สมัครด้วย Google/Apple พยายามขอรีเซ็ตรหัสผ่าน → ทำไม่ได้ เพราะไม่มีรหัสผ่านให้รีเซ็ต (REQ-16)
  - ผู้ใช้เปิดแอปมือถือ (companion app) โดยยังไม่เคยสมัคร/เข้าสู่ระบบบนเว็บมาก่อน → ใช้ [INT-2](#int-2--ซิงค์ตาชั่งอัจฉริยะ-req-12)/[INT-3](#int-3--ซิงค์ข้อมูล-wearable-req-13) ไม่ได้เลย
    เพราะมือถือไม่มีหน้าจอ auth ของตัวเอง ต้องมีบัญชีจากเว็บ (ONB-0) ก่อนเสมอ แล้วขอรหัสจับคู่อุปกรณ์
    (pairing-code) จากหน้าโปรไฟล์บนเว็บมากรอกบนมือถือแทน (ดู Steps ของ INT-2/INT-3 ด้านล่าง)
  - session หมดอายุ (ยังไม่กำหนดระยะเวลาที่แน่นอน ดู Open Questions) → ผู้ใช้ต้องเข้าสู่ระบบใหม่
  - ยังไม่ระบุว่าต้องมีขั้นตอนยืนยันอีเมล (email verification) ก่อนใช้งานได้จริงหรือไม่ — กระทบว่าเข้าสู่
    ONB-1 ได้ทันทีหลังสมัคร หรือต้องรอยืนยันอีเมลก่อน (ดู
    [จุดที่ยังไม่ได้ระบุของ Onboarding spec](../../01-requirements/01-spec/20260823-01-onboarding-personalization.md#จุดที่ยังไม่ได้ระบุ--ควรยืนยันเพิ่มเติม))
  - ยังไม่ระบุกติกาความซับซ้อนของรหัสผ่าน (password policy) สำหรับ email/password (ดู Open Questions)
  - ข้อมูลบัญชี/credential ต้องส่งผ่านการเชื่อมต่อที่เข้ารหัสเสมอ และการเก็บข้อมูลบัญชีผู้ใช้จริงเข้าเงื่อนไข
    PDPA (NFR-11) ที่ต้องมี consent record-keeping และสิทธิ์เข้าถึง/ลบข้อมูลของตนเอง (NFR-06) — เนื้อหา
    NFR-04/06/11 ควรถูก audit เพิ่มเติมว่าครบถ้วนสำหรับระบบบัญชีผู้ใช้จริงแล้วหรือไม่ (งานของ
    `test-suite-builder`, ดู
    [จุดที่ยังไม่ได้ระบุของ Onboarding spec](../../01-requirements/01-spec/20260823-01-onboarding-personalization.md#จุดที่ยังไม่ได้ระบุ--ควรยืนยันเพิ่มเติม))

### ONB-1 — กรอกข้อมูลส่วนตัวเพื่อคำนวณเป้าหมายแคลอรี่ (REQ-01)

```mermaid
flowchart TD
    A[เริ่ม Onboarding] --> B[กรอก อายุ/เพศ/น้ำหนัก/ส่วนสูง/กิจกรรม]
    B --> C{ข้อมูลถูกต้อง?}
    C -- ไม่ --> B
    C -- ใช่ --> D[คำนวณ BMR ด้วยสูตร Mifflin-St Jeor]
    D --> E[คูณด้วย Activity Factor ได้ TDEE]
    E --> F[บันทึก TDEE ลงโปรไฟล์]
    F --> G[ไปขั้นตอนเลือกอุปกรณ์ ONB-2]
```

**คำอธิบายตามลำดับ diagram:**

1. ผู้ใช้เริ่มขั้นตอน onboarding (REQ-01)
2. ผู้ใช้กรอกอายุ เพศ น้ำหนัก ส่วนสูง และเลือกระดับกิจกรรม (activity level) (REQ-01)
3. ระบบตรวจสอบความถูกต้องของค่าที่กรอก (เช่น ค่าติดลบ/เกินช่วงที่สมเหตุสมผล) — ถ้าไม่ผ่าน วนกลับไปให้แก้ไข (REQ-01)
4. เมื่อข้อมูลครบและถูกต้อง ระบบคำนวณ BMR (Basal Metabolic Rate) ด้วยสูตร Mifflin-St Jeor (REQ-01)
5. ระบบคูณ BMR ด้วยค่าสัมประสิทธิ์ระดับกิจกรรมเพื่อได้ TDEE (Total Daily Energy Expenditure) (REQ-01)
6. ระบบบันทึก TDEE ลงในโปรไฟล์ผู้ใช้ (REQ-01)
7. ไปต่อยังขั้นตอนเลือกอุปกรณ์ (ONB-2)

- **Actor/Persona**: ผู้ใช้ใหม่ (First-time user) ที่เพิ่งติดตั้งแอป
- **Goal**: เพื่อให้ระบบคำนวณเป้าหมายแคลอรี่รายวันให้ตนเอง
- **Trigger**: เปิดแอปครั้งแรกและเข้าสู่ขั้นตอน onboarding
- **Preconditions**: มีบัญชีผู้ใช้ (`userId`) จริงแล้วจาก ONB-0 (สมัครสมาชิก/เข้าสู่ระบบ) และยังไม่เคยตั้งค่า
  โปรไฟล์ร่างกายมาก่อน
- **Success State**: ผู้ใช้มีค่า TDEE ที่คำนวณแล้วในโปรไฟล์ ใช้เป็น baseline สำหรับ ONB-3 และ REC-1 (REQ-01)
- **Alt/Edge Cases**:
  - กรอกข้อมูลไม่ครบ/ไม่ถูกต้อง → ระบบไม่ให้ไปขั้นตอนถัดไปจนกว่าจะแก้ไข
  - ผู้ใช้แก้ไขน้ำหนัก/ส่วนสูงภายหลัง (เช่นจาก ONB profile settings หรือ INT-2) → ต้องคำนวณ BMR/TDEE ใหม่
  - การคำนวณ BMR/TDEE เป็น client-side ล้วน ไม่มี network latency เกี่ยวข้อง (NFR-03) และข้อมูลร่างกาย
    ที่กรอกในขั้นตอนนี้ต้องเข้ารหัสทั้งระหว่างส่งและจัดเก็บเมื่อมี backend จริง (NFR-04)

### ONB-2 — เลือกอุปกรณ์ที่มี (REQ-03)

```mermaid
flowchart TD
    A[เข้าสู่ขั้นตอนเลือกอุปกรณ์] --> B[แสดงตัวเลือก: ไม่มี/ดัมเบล/ยิมครบชุด]
    B --> C[ผู้ใช้เลือกอุปกรณ์]
    C --> D[บันทึกโปรไฟล์อุปกรณ์]
    D --> E[ใช้เป็น filter ในเอนจิ้นแนะนำวิดีโอ REC-1]
```

**คำอธิบายตามลำดับ diagram:**

1. ผู้ใช้มาถึงขั้นตอนเลือกอุปกรณ์ใน onboarding หรือหน้า Settings (REQ-03)
2. ระบบแสดงตัวเลือกอุปกรณ์: ไม่มีอุปกรณ์ / ดัมเบล / ยิมครบชุด (REQ-03)
3. ผู้ใช้เลือกอุปกรณ์ที่มีได้มากกว่า 1 ประเภทพร้อมกัน ตาม
   [decision ที่ resolve แล้วใน Onboarding spec](../../01-requirements/01-spec/20260823-01-onboarding-personalization.md#ข้อสมมติฐานการตัดสินใจที่ยืนยันแล้ว)
   (REQ-03)
4. ระบบบันทึกโปรไฟล์อุปกรณ์ของผู้ใช้ (REQ-03)
5. โปรไฟล์อุปกรณ์นี้ถูกใช้เป็น filter ในเอนจิ้นแนะนำวิดีโอ (REC-1) ทุกครั้งที่ค้นหาวิดีโอ (REQ-03)

- **Actor/Persona**: ผู้ใช้ใหม่ (ระหว่าง onboarding) หรือผู้ใช้ประจำที่แก้ไขโปรไฟล์
- **Goal**: เพื่อให้ระบบแนะนำท่า/วิดีโอที่ทำได้จริงตามอุปกรณ์ที่มี
- **Trigger**: มาถึงขั้นตอนเลือกอุปกรณ์ใน onboarding หรือเข้าไปแก้ไขในหน้า Settings
- **Preconditions**: ผ่าน ONB-1 แล้ว (มี TDEE ในโปรไฟล์)
- **Success State**: โปรไฟล์อุปกรณ์ถูกบันทึก และวิดีโอที่แนะนำในอนาคตทั้งหมดถูกกรองด้วยอุปกรณ์นี้ (REQ-03)
- **Alt/Edge Cases**:
  - เลือก "ไม่มีอุปกรณ์" → ระบบกรองเฉพาะวิดีโอ bodyweight เท่านั้น
  - ผู้ใช้เปลี่ยนอุปกรณ์ภายหลัง (เช่น ซื้อดัมเบลเพิ่ม) → filter ในการแนะนำวิดีโอครั้งถัดไปอัปเดตทันที

### ONB-3 — ตั้งเป้าหมายหลัก (REQ-02)

```mermaid
flowchart TD
    A[เลือกเป้าหมายหลัก] --> B{ประเภทเป้าหมาย}
    B -- ลดน้ำหนัก --> C["Target kcal = TDEE − 500/วัน + กรอกน้ำหนักเป้าหมาย (บังคับ)"]
    B -- กระชับสัดส่วน --> D["Target kcal = TDEE + 0/วัน (maintenance) + น้ำหนักเป้าหมาย (ไม่บังคับ)"]
    B -- เพิ่มความอึด --> E["Target kcal = TDEE + 300/วัน + น้ำหนักเป้าหมาย (ไม่บังคับ)"]
    C --> F{"Target kcal < Safety Floor 1,200–1,500 kcal?"}
    D --> F
    E --> F
    F -- ใช่ ต่ำกว่า floor --> G[ปรับ Target kcal = Safety Floor]
    F -- ไม่ อยู่ในเกณฑ์ --> H[ใช้ Target kcal ตามที่คำนวณ]
    G --> I["บันทึกเป้าหมายแคลอรี่รายวัน + น้ำหนักเป้าหมาย (ถ้ามี) + Onboarding เสร็จสมบูรณ์"]
    H --> I
```

**คำอธิบายตามลำดับ diagram:**

1. ผู้ใช้เลือกเป้าหมายหลัก: ลดน้ำหนัก / กระชับสัดส่วน / เพิ่มความอึด (REQ-02)
2. ระบบแปลงเป้าหมายเป็นค่าคงที่ตายตัวตาม decision ที่ resolve แล้ว พร้อมให้กรอกน้ำหนักเป้าหมาย (target
   weight, kg) ตามประเภทที่เลือก — ตาม
   [decision ที่ resolve แล้วเมื่อ 2026-08-28](../../01-requirements/01-spec/20260823-01-onboarding-personalization.md#ข้อสมมติฐานการตัดสินใจที่ยืนยันแล้ว):
   - ลดน้ำหนัก → Target kcal = TDEE − 500 kcal/วัน และกรอกน้ำหนักเป้าหมายเป็น**ช่องบังคับ** (REQ-02)
   - กระชับสัดส่วน → Target kcal = TDEE + 0 kcal/วัน (maintenance) และกรอกน้ำหนักเป้าหมายเป็น
     **ช่องไม่บังคับ** (REQ-02)
   - เพิ่มความอึด → Target kcal = TDEE + 300 kcal/วัน และกรอกน้ำหนักเป้าหมายเป็น**ช่องไม่บังคับ** (REQ-02)
3. ระบบตรวจสอบว่า Target kcal ที่ได้ต่ำกว่า safety floor (1,200–1,500 kcal/วัน) หรือไม่ (REQ-02)
4. ถ้าต่ำกว่า floor → ปรับ Target kcal ให้เท่ากับ safety floor แทน (REQ-02); ถ้าไม่ต่ำกว่า floor → ใช้ Target kcal ตามที่คำนวณได้ (REQ-02)
5. ระบบบันทึกเป้าหมายแคลอรี่รายวันสุดท้าย พร้อมน้ำหนักเป้าหมาย (ถ้ามีการกรอก) ลงโปรไฟล์ พร้อม onboarding
   เสร็จสมบูรณ์ (REQ-02)

- **Actor/Persona**: ผู้ใช้ใหม่ (ระหว่าง onboarding)
- **Goal**: เพื่อกำหนดทิศทางแผนการออกกำลังกายและแคลอรี่ให้ตรงกับเป้าหมาย
- **Trigger**: มาถึงขั้นตอนสุดท้ายของ onboarding หลังมี TDEE (ONB-1) แล้ว
- **Preconditions**: ผ่าน ONB-1 (มี TDEE)
- **Success State**: ผู้ใช้มีเป้าหมายแคลอรี่รายวันที่ชัดเจน (TDEE ± ค่าคงที่ต่อเป้าหมาย และไม่ต่ำกว่า
  safety floor) พร้อมเข้าสู่หน้า Daily Recommendation (REQ-02) และ (เมื่อเลือก "ลดน้ำหนัก" หรือกรอกไว้แม้
  ไม่บังคับ) มีน้ำหนักเป้าหมาย (target weight) บันทึกไว้ในโปรไฟล์ด้วย ค่าคงที่ 7,700 kcal ≈ 1 กก. ไขมัน
  ที่ผูกกับเป้าหมายนี้ถูกใช้ร่วมกับ INT-1 ในการพยากรณ์วันถึงเป้าหมายน้ำหนักด้วย
- **Alt/Edge Cases**:
  - ผู้ใช้เปลี่ยนเป้าหมายหลักภายหลัง (เช่น จากลดน้ำหนักเป็นเพิ่มความอึด) → คำนวณเป้าหมายแคลอรี่รายวันใหม่ทันทีด้วยสูตรคงที่เดิม
  - TDEE ของผู้ใช้ต่ำมาก (เช่น น้ำหนักตัวน้อย + กิจกรรมต่ำ) จนแม้แต่ TDEE + 300 ยังต่ำกว่า floor →
    ระบบปรับขึ้นเป็น safety floor เสมอ ไม่ปล่อยให้ต่ำกว่าเกณฑ์
  - ผู้ใช้เลือก "กระชับสัดส่วน"/"เพิ่มความอึด" แล้วข้ามช่องน้ำหนักเป้าหมาย (ไม่บังคับ) → INT-1 จะยังใช้
    พยากรณ์วันถึงเป้าหมายน้ำหนักให้ไม่ได้ จนกว่าผู้ใช้จะกรอกน้ำหนักเป้าหมายภายหลัง (ช่องทางที่แน่ชัดยังไม่
    ระบุ ดู [จุดที่ยังไม่ได้ระบุของ Onboarding spec](../../01-requirements/01-spec/20260823-01-onboarding-personalization.md#จุดที่ยังไม่ได้ระบุ--ควรยืนยันเพิ่มเติม))

- **Success State**: มีค่าแคลอรี่เผาผลาญจริงต่อเซสชัน คำนวณจากสูตร MET (MET × น้ำหนักตัว × เวลา) ไม่ใช่ชื่อวิดีโอ (REQ-05)

  - มีข้อมูล wearable ระหว่างออกกำลังกาย → ให้ความสำคัญกับค่าจาก wearable มากกว่าค่าประมาณจากสูตร MET (ดู INT-3)
  - การคำนวณสูตร MET เป็น client-side ล้วน ไม่มี network latency เกี่ยวข้อง (NFR-03)

**คำอธิบายตามลำดับ diagram:**

1. ผู้ใช้เปิดแท็บ Planner/ปฏิทิน ระบบแสดงปฏิทินแบบ **fixed calendar week (จันทร์–อาทิตย์)** ตาม
   [decision ที่ resolve แล้ว](../../01-requirements/01-spec/20260823-03-planner-logging.md#ข้อสมมติฐานการตัดสินใจที่ยืนยันแล้ว)
   (ไม่ใช่ rolling 7-day-forward window) (REQ-08)
2. ผู้ใช้เลือกวันที่ต้องการดู/วางแผนในสัปดาห์นั้น (REQ-08)
3. ระบบตรวจสอบว่าวันนั้นเป็นวันที่ผ่านมาแล้วและมี log บันทึกไว้ก่อนแล้วหรือไม่ (REQ-08)
4. **กรณีเป็นวันที่ผ่านมาแล้วและมี log**: เปิดชีทรายละเอียดวันแบบ **read-only แก้ไขไม่ได้** (REQ-08)
5. **กรณีเป็นวันนี้หรือวันในอนาคตของสัปดาห์เดียวกัน (ยังไม่มี log)**: ผู้ใช้เลือกว่าจะกำหนดประเภทกิจกรรมเอง,
   ตั้งเป็น Cheat Day/Rest Day (ไปต่อที่ PLN-2), หรือปล่อยว่าง (REQ-08)
6. ถ้ากำหนดเอง → บันทึกประเภทกิจกรรมของวันนั้น; ถ้าปล่อยว่าง → ใช้ค่า default คือให้ระบบแนะนำอัตโนมัติตาม REC-1 (REQ-08)
7. ระบบบันทึกแผนรายสัปดาห์ไว้ ใช้แสดงผลใน Daily Dashboard ของแต่ละวัน (REQ-08)

- **Actor/Persona**: ผู้ใช้ประจำที่ต้องการวางแผนล่วงหน้า
- **Goal**: วางแผนออกกำลังกายล่วงหน้าเป็นสัปดาห์ ไม่ต้องตัดสินใจรายวัน
- **Trigger**: ผู้ใช้เปิดแท็บ Planner/ปฏิทิน
- **Preconditions**: ผ่าน onboarding แล้ว (มีเป้าหมายแคลอรี่รายวัน)
- **Success State**: ผู้ใช้เห็นปฏิทินรายสัปดาห์แบบจันทร์–อาทิตย์ครบสัปดาห์ พร้อมกำหนดแผนของวันนี้/วันในอนาคต
  ได้ ส่วนวันที่ผ่านมาแล้วซึ่งมี log อยู่ก่อนแสดงเป็น read-only (REQ-08)
- **Alt/Edge Cases**:
  - ผู้ใช้ไม่กำหนดแผนล่วงหน้าในบางวัน → วันนั้นใช้ค่า default คือให้ระบบแนะนำอัตโนมัติตาม REC-1
  - ผู้ใช้แก้ไขแผนของวันที่ผ่านไปแล้ว (มี log แล้ว) ได้หรือไม่ → **resolve แล้ว: แก้ไขไม่ได้ เปิดดูได้แบบ
    read-only เท่านั้น** ตาม decision ที่ยืนยันในสเปคด้านบน (เดิมเป็น Open Question ปิดแล้วเมื่อ 2026-08-27)

### PLN-2 — โหมด Cheat Day / Rest Day (REQ-09)

```mermaid
flowchart TD
    A[ผู้ใช้เลือกวันที่จะตั้ง Cheat Day หรือ Rest Day] --> A2{วันนั้นเป็นวันในอดีตของสัปดาห์และมี log อยู่แล้วหรือไม่?}
    A2 -- ใช่ ในอดีต + มี log --> A3["ปิดกั้น — วันนั้น read-only ตาม PLN-1 (ไม่มีข้อยกเว้นสำหรับ PLN-2)"]
    A2 -- ไม่ วันนี้/วันในอนาคต --> B{วันนั้นมี log อยู่แล้วหรือไม่?}
    B -- ไม่มี log --> C["หยุดนับเป้าหมายแคลอรี่ของวันนั้น + ไม่แนะนำวิดีโอ (ข้าม REC-1)"]
    C --> D["Mark สถานะวันนั้น = ครบเป้าหมาย (completed)"]
    B -- มี log อยู่แล้ว เฉพาะวันนี้เท่านั้น --> E[เก็บ log เดิมไว้ ไม่ลบทิ้ง]
    E --> F["Mark สถานะวันนั้น = ครบเป้าหมาย (completed) — completed ชนะเสมอ"]
    D --> G[Streak ไม่ขาด ต่อเนื่องในวันถัดไปที่ออกกำลังกายจริง]
    F --> G
```

**คำอธิบายตามลำดับ diagram:**

1. ผู้ใช้เลือกวันที่ต้องการตั้ง Cheat Day หรือ Rest Day ผ่านปฏิทิน (PLN-1) หรือหน้า Daily Dashboard (REQ-09)
2. ระบบตรวจสอบก่อนว่าวันนั้นเป็นวันในอดีตของสัปดาห์ (fixed calendar week ของ PLN-1) ที่มี log อยู่แล้วหรือไม่
   ตาม decision ที่ resolve แล้วเมื่อ 2026-08-28: **ถ้าใช่ → ปิดกั้นทันที วันนั้นเป็น read-only ตาม decision
   ของ PLN-1 ไม่มีข้อยกเว้นสำหรับ PLN-2** — การตั้ง/เปลี่ยน Cheat/Rest Day ที่ทับ log ซึ่งมีอยู่แล้ว ทำได้
   เฉพาะ **"วันนี้" เท่านั้น** (เช่น หลังออกกำลังกายเสร็จในวันเดียวกัน) ไม่สามารถทำผ่านการแตะวันในอดีตของ
   สัปดาห์จากปฏิทินได้อีกต่อไป (ยืนยันแล้วใน
   [Planner spec § ข้อสมมติฐาน/การตัดสินใจที่ยืนยันแล้ว](../../01-requirements/01-spec/20260823-03-planner-logging.md#ข้อสมมติฐานการตัดสินใจที่ยืนยันแล้ว))
   (REQ-09)
3. **กรณีเป็นวันนี้หรือวันในอนาคต**: ระบบตรวจสอบต่อว่าวันนั้นมี log อยู่แล้วหรือไม่ (REQ-09)
4. **กรณียังไม่มี log**: ระบบหยุดนับเป้าหมายแคลอรี่ของวันนั้น และไม่แนะนำวิดีโอสำหรับวันนั้น (ข้าม REC-1) (REQ-09)
5. **กรณียังไม่มี log** (ต่อ): ระบบ mark สถานะวันนั้นเป็น "ครบเป้าหมาย" (completed) (REQ-09)
6. **กรณีมี log อยู่แล้วก่อนตั้ง Cheat/Rest Day (เฉพาะวันนี้เท่านั้น)**: ระบบเก็บ log เดิมไว้ทั้งหมด
   ไม่ลบทิ้ง (REQ-09)
7. **กรณีมี log อยู่แล้ว** (ต่อ): สถานะวันนั้นยังคง mark เป็น "ครบเป้าหมาย" (completed) — กติกา
   "completed ชนะเสมอ" หมายความว่า Cheat/Rest Day ไม่ไปเปลี่ยนสถานะ log ที่มีอยู่ก่อนให้แย่ลง (REQ-09)
8. ไม่ว่าจะเป็นกรณีใด (ยกเว้นกรณีถูกปิดกั้นในข้อ 2) ผลลัพธ์คือ streak ไม่ขาด และต่อเนื่องในวันถัดไปที่
   ออกกำลังกายจริง (เชื่อมกับ PLN-4) (REQ-09)

- **Actor/Persona**: ผู้ใช้ประจำที่ต้องการพักหรือของ่อนวันโดยไม่เสียสถิติ
- **Goal**: หยุดพัก/ผ่อนคลายได้ 1 วัน โดยไม่ทำให้ streak หรือสถิติเสียหาย
- **Trigger**: ผู้ใช้ตั้งค่า Cheat Day หรือ Rest Day ผ่านปฏิทิน (PLN-1) หรือในหน้า Daily Dashboard ของวันนั้น
  — การทับ log ที่มีอยู่แล้วทำได้เฉพาะเมื่อ trigger เกิดขึ้น **ในวันนี้เท่านั้น**
- **Preconditions**: มีเป้าหมายแคลอรี่รายวันที่กำลังทำงานอยู่สำหรับวันนั้น และถ้าวันนั้นมี log อยู่แล้ว
  จะต้องเป็นวันนี้เท่านั้น (ไม่ใช่วันในอดีตของสัปดาห์ ซึ่งเป็น read-only ตาม PLN-1)
- **Success State**: วันนั้นถูก mark เป็น "ครบเป้าหมาย" (completed) เสมอ — ไม่ว่าจะมี log อยู่ก่อนหรือไม่ —
  และ streak ยังคงต่อเนื่องในวันถัดไปที่ออกกำลังกายจริง (REQ-09)
- **Alt/Edge Cases**:
  - ผู้ใช้ทำเครื่องหมาย Cheat/Rest Day **หลังจาก**ออกกำลังกายและมี log ของวันนั้นแล้ว (ต้องเป็นวันนี้เท่านั้น)
    → ตาม decision ที่ resolve แล้ว: **เก็บ log เดิมไว้ ไม่ลบทิ้ง และวันนั้นยังคงถือว่า "ครบเป้าหมาย"
    (completed)** ไม่ว่า log เดิมจะเป็นสถานะครบเป้าหมายหรือไม่ครบเป้าหมายก็ตาม — Cheat/Rest Day มีผลเปลี่ยน
    สถานะเฉพาะวันที่ยังไม่มี log หรือวันนี้ที่มี log แล้วเท่านั้น
  - ผู้ใช้พยายามตั้ง/เปลี่ยน Cheat/Rest Day ทับ log ของวันในอดีตของสัปดาห์ (ผ่านการแตะวันนั้นจากปฏิทิน PLN-1)
    → **resolve แล้วเมื่อ 2026-08-28: ทำไม่ได้** วันนั้นเปิดได้แบบ read-only เท่านั้น ตาม decision ของ PLN-1
    ไม่มีข้อยกเว้นสำหรับ PLN-2 (เดิมเป็นคำถามที่ `test-suite-builder` พบระหว่าง self-freshness audit — ปิด
    แล้ว)
  - ผู้ใช้ยกเลิกการตั้ง Cheat/Rest Day ก่อนสิ้นวัน → วันนั้นกลับไปนับเป้าหมายแคลอรี่ตามปกติ (ประเมินใหม่ตาม PLN-3)
  - การตั้ง Cheat/Rest Day ต้องแสดง feedback ทาง UI ทันทีภายใน 250ms แบบ optimistic UI ไม่ต้องรอ network
    response ก่อน (NFR-02)

### PLN-3 — บันทึกผลรายวันเมื่อครบเป้าหมาย (REQ-10)

```mermaid
flowchart TD
    A[ผู้ใช้ออกกำลังกาย] --> B[เทียบแคลอรี่จริง REC-2 กับเป้าหมายของวัน]
    B --> C{"ถึงหรือเกินเป้าหมาย 100%?"}
    C -- ใช่ ครบ 100% --> D["สร้าง log: นาที, แคลอรี่สะสม, สถานะ = ครบเป้าหมาย"]
    C -- ไม่ แม้ใกล้เคียงแค่ไหนก็ตาม --> E["สร้าง log สถานะ = ไม่ครบเป้าหมาย (ไม่มี partial credit)"]
    D --> F[อัปเดตสถิติรวม + ส่งต่อสถานะให้ PLN-4]
    E --> F
```

**คำอธิบายตามลำดับ diagram:**

1. ผู้ใช้ทำวิดีโอออกกำลังกายจนจบหรือหยุด (REQ-10)
2. ระบบเปรียบเทียบแคลอรี่ที่เผาผลาญจริง (REC-2) กับเป้าหมายแคลอรี่ของวันนั้น (จาก ONB-3/REC-1) (REQ-10)
3. ระบบตัดสินด้วยกติกา **all-or-nothing เข้มงวด** ตาม decision ที่ resolve แล้ว: ถึงหรือเกินเป้าหมาย
   100% เท่านั้นจึงถือว่า "ครบเป้าหมาย" (REQ-10)
4. **กรณีถึง 100%**: สร้าง log entry ประกอบด้วยนาทีที่ออกกำลังกายจริง, แคลอรี่ที่เผาผลาญสะสม, วันที่,
   สถานะ "ครบเป้าหมาย" (REQ-10)
5. **กรณีไม่ถึง 100%** (แม้จะใกล้เคียงเพียงเล็กน้อย): สร้าง log สถานะ "ไม่ครบเป้าหมาย" โดยไม่มี partial
   credit ใด ๆ (REQ-10)
6. ไม่ว่าผลจะเป็นสถานะใด ระบบอัปเดตสถิติรวมของผู้ใช้ และส่งต่อสถานะของวันนี้ให้ PLN-4 ใช้คำนวณ streak (REQ-10)

- **Actor/Persona**: ผู้ใช้ประจำที่เพิ่งออกกำลังกายเสร็จ
- **Goal**: มีบันทึกผลการออกกำลังกายของตัวเองไว้ดูย้อนหลัง
- **Trigger**: ผู้ใช้ทำวิดีโอออกกำลังกายจนครบ (หรือไม่ครบ) เป้าหมายแคลอรี่/เวลาของวันนั้น
- **Preconditions**: มีค่าแคลอรี่เผาผลาญจริงจาก REC-2 และเป้าหมายแคลอรี่ของวันจาก ONB-3/REC-1
- **Success State**: มี log รายวันที่บันทึกนาทีออกกำลังกายและแคลอรี่สะสม พร้อมสถานะ "ครบเป้าหมาย" เฉพาะเมื่อ
  ถึงหรือเกินเป้าหมาย 100% เท่านั้น (REQ-10)
- **Alt/Edge Cases**:
  - ออกกำลังกายแล้วแต่ยังไม่ถึงเป้าหมาย (เช่น ทำได้ 95%) → บันทึกเป็น log สถานะ "ไม่ครบเป้าหมาย" ตาม
    กติกา all-or-nothing เข้มงวด — ไม่มี partial credit หรือเกณฑ์ผ่อนปรนใด ๆ ในเวอร์ชันนี้
  - วันนั้นเป็น Cheat Day/Rest Day → ข้ามขั้นตอนนี้ทั้งหมด สถานะถูกกำหนดโดย PLN-2 แทน
  - การบันทึกผลรายวันต้องแสดง feedback ทาง UI ทันทีภายใน 250ms แบบ optimistic UI (NFR-02) และ log ต้องมี
    local persistence ก่อน sync ขึ้น backend เพื่อไม่ให้หายเมื่อ network ไม่เสถียร (NFR-08)

### PLN-4 — ติดตาม Streak ต่อเนื่อง (REQ-09, REQ-10)

```mermaid
flowchart TD
    A[เริ่มคำนวณ Streak จากวันนี้ย้อนหลัง] --> B{สถานะของวันนั้น}
    B -- "ครบเป้าหมาย (completed) จาก PLN-3 หรือ PLN-2" --> C[นับต่อเนื่อง ไปวันก่อนหน้า]
    C --> B
    B -- "ไม่ครบเป้าหมาย หรือไม่มี log เลย" --> D["Streak ขาดทันที (ไม่มี partial credit / grace miss)"]
    D --> E[รีเซ็ต Streak เป็น 0 ที่วันนั้น]
    C --> F[แสดงจำนวนวัน Streak บน Dashboard]
    E --> F
```

**คำอธิบายตามลำดับ diagram:**

1. ระบบเริ่มไล่ log ย้อนหลังจากวันปัจจุบันเพื่อคำนวณ streak (REQ-10)
2. สำหรับแต่ละวัน ระบบตรวจสอบสถานะของวันนั้น (REQ-09, REQ-10)
3. ถ้าสถานะเป็น "ครบเป้าหมาย" (completed) — ไม่ว่าจะมาจาก log จริงที่ครบ 100% ใน PLN-3 หรือจาก
   Cheat/Rest Day ใน PLN-2 — ให้นับว่า streak ยังต่อเนื่อง แล้วไปตรวจวันก่อนหน้าต่อ (REQ-09)
4. ถ้าสถานะเป็น "ไม่ครบเป้าหมาย" (จาก PLN-3) หรือไม่มี log เลย ระบบใช้กติกา **all-or-nothing เข้มงวด**
   ตาม decision ที่ resolve แล้ว: **ถือว่า streak ขาดทันที เหมือนไม่มี log เลย ไม่มี partial credit หรือ
   grace miss ใด ๆ** (REQ-10)
5. เมื่อพบวันที่ทำให้ขาด ระบบรีเซ็ต streak เป็น 0 ที่วันนั้น (REQ-10)
6. ระบบคำนวณจำนวนวันติดต่อกัน และแสดงผลเป็นตัวเลข streak บน Dashboard (REQ-09, REQ-10)

- **Actor/Persona**: ผู้ใช้ประจำที่ต้องการแรงจูงใจให้ออกกำลังกายต่อเนื่อง
- **Goal**: เห็น streak การออกกำลังกายต่อเนื่องของตัวเอง เพื่อกระตุ้นให้ทำต่อ
- **Trigger**: เปิดหน้า Dashboard/Stats หรือหลังบันทึก log รายวันสำเร็จ (PLN-3) หรือหลังตั้ง Cheat/Rest Day (PLN-2)
- **Preconditions**: มีประวัติ log อย่างน้อย 1 วัน
- **Success State**: ผู้ใช้เห็นจำนวนวัน streak ปัจจุบันที่ถูกต้องตามกฎ all-or-nothing เข้มงวด — นับต่อเนื่อง
  เฉพาะวันที่ "ครบเป้าหมาย" จริง (PLN-3) หรือ Cheat/Rest Day (PLN-2) เท่านั้น (REQ-09, REQ-10)
- **Alt/Edge Cases**:
  - ผู้ใช้ขาด log ไป 1 วันโดยไม่ได้ตั้ง Cheat/Rest Day → streak รีเซ็ตเป็น 0 ทันที
  - log สถานะ "ไม่ครบเป้าหมาย" จาก PLN-3 (เช่น ทำได้ 90-99%) → **ทำให้ streak ขาดทันทีเหมือนไม่มี log
    เลย** ตาม decision ที่ resolve แล้ว ไม่มีเกณฑ์ผ่อนปรนบางส่วนในเวอร์ชันนี้
  - ข้อมูล streak ต้องไม่สูญหายจาก network เชื่อมต่อไม่เสถียร (local persistence ก่อน sync — NFR-08)

## Epic 4: Smart Integrations

ทุก feature ใน Epic นี้ (INT-0, INT-1, INT-2, INT-3) เป็น MoSCoW = Could — INT-0 เป็น precondition
ทางเทคนิคร่วมของ INT-2/INT-3 (ไม่มี feature Must/Should ใดพึ่งพา) ส่วน INT-1/INT-2/INT-3 เป็นแหล่งข้อมูล
ทางเลือกเท่านั้น —
core loop รายวัน (ONB → REC-1 → PLN-3) ต้องยังใช้งานได้แม้ Epic นี้ทั้งหมดจะ unavailable/error โดยระบบต้อง
fallback อย่างสงบ ไม่ใช้ error ที่ทำให้ผู้ใช้ตกใจ (NFR-07) และการเชื่อมต่อ Health API/wearable (INT-3) หรือ
ตาชั่งอัจฉริยะผ่าน Bluetooth (INT-2) ทุกครั้งต้องขอ consent จากผู้ใช้อย่างชัดเจนก่อนเสมอ (OAuth/system
permission prompt) ห้าม auto-connect โดยไม่ถาม (NFR-05)

### INT-0 — ยืนยันตัวตนก่อนจับคู่อุปกรณ์ผ่านรหัสจับคู่ (REQ-18)

```mermaid
flowchart TD
    A["ผู้ใช้ล็อกอินอยู่บนเว็บแอปแล้ว (ONB-0) เปิดหน้าโปรไฟล์"] --> B[กดขอรหัสจับคู่อุปกรณ์]
    B --> C["Server สร้างรหัสจับคู่ 6 หลัก อายุ 5 นาที แสดงบนหน้าเว็บ"]
    C --> D[เปิด companion app บนมือถือ กรอกรหัสจับคู่]
    D --> E{รหัสถูกต้อง ไม่หมดอายุ และยังไม่ถูกใช้?}
    E -- ไม่ --> D
    E -- ใช่ --> F["Server mint token ผูกกับบัญชีเดิม มือถือ sign in แบบ silent"]
    F --> G["เข้าสู่หน้าจับคู่อุปกรณ์จริง (INT-2 หรือ INT-3)"]
```

**คำอธิบายตามลำดับ diagram:**

1. ผู้ใช้ที่ล็อกอินอยู่แล้วบนเว็บแอปจาก [ONB-0](#onb-0--สมัครสมาชิก--เข้าสู่ระบบ--ลืมรหัสผ่าน--ออกจากระบบ-req-14-req-15-req-16-req-17)
   เปิดหน้าโปรไฟล์ — precondition ของทั้ง flow นี้คือมีบัญชีผู้ใช้จากเว็บอยู่แล้วเสมอ (REQ-18)
2. ผู้ใช้กดขอรหัสจับคู่อุปกรณ์จากหน้าโปรไฟล์ (REQ-18)
3. Server สร้างรหัสจับคู่แบบตัวเลข 6 หลัก อายุการใช้งาน **5 นาที** ผูกกับบัญชีผู้ใช้ที่ล็อกอินอยู่ขณะนั้น
   แสดงบนหน้าจอเว็บ (REQ-18)
4. ผู้ใช้เปิด companion app บนมือถือ (แอปมือถือไม่มีหน้าจอ auth ของตัวเอง ดู ONB-0) กรอกรหัส 6 หลักนั้น (REQ-18)
5. ระบบตรวจสอบว่ารหัสถูกต้อง ยังไม่หมดอายุ และยังไม่เคยถูกใช้ (**single-use**) หรือไม่ — ถ้าไม่ผ่าน วนกลับ
   ไปให้กรอกรหัสใหม่ (REQ-18)
6. ถ้าผ่าน → server mint short-lived token ผูกกับบัญชีเดิมที่สร้างรหัสไว้ มือถือใช้ token นั้น sign in
   แบบ silent (ไม่ต้องกรอกรหัสผ่านซ้ำ) (REQ-18)
7. มือถือเข้าสู่หน้าจับคู่อุปกรณ์จริง — [INT-2](#int-2--ซิงค์ตาชั่งอัจฉริยะ-req-12) (ตาชั่งอัจฉริยะ) หรือ
   [INT-3](#int-3--ซิงค์ข้อมูล-wearable-req-13) (wearable) แล้วแต่ว่าผู้ใช้ต้องการจับคู่อุปกรณ์ชนิดใด (REQ-18)

- **Actor/Persona**: ผู้ใช้ประจำที่มีบัญชีจากเว็บแอปอยู่แล้ว (ONB-0) และต้องการจับคู่อุปกรณ์ (ตาชั่งอัจฉริยะ
  หรือ wearable) ผ่าน companion mobile app
- **Goal**: ยืนยันตัวตนบนมือถือได้โดยไม่ต้องมีหน้าจอ auth ของตัวเอง เพื่อเข้าสู่ขั้นตอนจับคู่อุปกรณ์จริง
- **Trigger**: ผู้ใช้เปิด companion app ครั้งแรก (หรือ session มือถือหมดอายุ/ยังไม่เคยยืนยันตัวตน) แล้ว
  ต้องการจับคู่อุปกรณ์ (INT-2 หรือ INT-3)
- **Preconditions**: มีบัญชีผู้ใช้ที่ล็อกอินอยู่บนเว็บแอปแล้ว ([ONB-0](#onb-0--สมัครสมาชิก--เข้าสู่ระบบ--ลืมรหัสผ่าน--ออกจากระบบ-req-14-req-15-req-16-req-17))
  — เพราะมือถือไม่มีหน้าจอ auth ของตัวเอง
- **Success State**: มือถือได้รับ session ที่ authenticated ผูกกับบัญชีผู้ใช้เดิม พร้อมเข้าสู่หน้าจับคู่
  อุปกรณ์จริง (INT-2/INT-3) ได้โดยไม่ต้องกรอก credential ซ้ำ (REQ-18)
- **Alt/Edge Cases**:
  - รหัสจับคู่หมดอายุ (เกิน 5 นาที) หรือถูกใช้ไปแล้ว (single-use) → มือถือกรอกไม่ผ่าน ต้องขอรหัสใหม่จากเว็บ
  - ผู้ใช้เปิด companion app โดยยังไม่มีบัญชีจากเว็บมาก่อนเลย → ยังขอรหัสจับคู่ไม่ได้เลย จนกว่าจะสมัคร/
    เข้าสู่ระบบบนเว็บก่อน (ดู [ONB-0](#onb-0--สมัครสมาชิก--เข้าสู่ระบบ--ลืมรหัสผ่าน--ออกจากระบบ-req-14-req-15-req-16-req-17))
  - รหัสจับคู่และ token ที่ mint ต้องส่งผ่านการเชื่อมต่อที่เข้ารหัสเสมอ เช่นเดียวกับข้อมูลบัญชี/credential
    ของ ONB-0 (NFR-04 ลักษณะเดียวกัน)
  - ยังไม่ได้ระบุกติกา rate limiting เมื่อกรอกรหัสผิดซ้ำ ๆ หลายครั้งติดกันบนมือถือ (ดู
    [จุดที่ยังไม่ได้ระบุของ Smart Integrations spec](../../01-requirements/01-spec/20260823-04-smart-integrations.md#จุดที่ยังไม่ได้ระบุ--ควรยืนยันเพิ่มเติม))

### INT-1 — พยากรณ์วันถึงเป้าหมายน้ำหนัก (REQ-11)

```mermaid
flowchart TD
    A[เปิดหน้า Progress/Insights] --> A2{มีน้ำหนักเป้าหมาย จาก ONB-3 หรือไม่?}
```

   แล้วข้ามช่องไม่บังคับ (REQ-11)
3. **กรณีไม่มีน้ำหนักเป้าหมาย**: แจ้งผู้ใช้ว่ายังพยากรณ์ไม่ได้ ให้ไปกรอกน้ำหนักเป้าหมายที่ ONB-3/โปรไฟล์ก่อน (REQ-11)
4. **กรณีมีน้ำหนักเป้าหมาย**: ระบบตรวจสอบว่ามีประวัติ log แคลอรี่จริงสะสมเพียงพอหรือไม่ (REQ-11)
5. ถ้าไม่เพียงพอ → แจ้งผู้ใช้ว่ายังพยากรณ์ไม่ได้ ต้องสะสมข้อมูลเพิ่ม (REQ-11)
6. ถ้าเพียงพอ → ระบบดึงประวัติแคลอรี่ขาดดุล/เกินดุลจริงที่บันทึกไว้จาก log จริง (PLN-3) ไม่ใช่ค่าประมาณตอน
   onboarding แล้วคำนวณอัตราขาดดุลแคลอรี่เฉลี่ยต่อวันจากช่วงเวลาล่าสุด (REQ-11)
7. ระบบแปลงอัตราขาดดุลเฉลี่ยเป็นอัตราการเปลี่ยนแปลงน้ำหนักโดยประมาณ โดยใช้ค่าคงที่ **7,700 kcal ≈ 1 กก.
   ไขมัน** ตาม decision ของ ONB-3/REQ-02 ที่ resolve แล้ว (REQ-11)
8. ระบบคำนวณวันที่คาดว่าจะถึงน้ำหนักเป้าหมายจากน้ำหนักปัจจุบันและอัตรานี้ (REQ-11)
9. แสดงวันที่คาดการณ์บนหน้า Progress (REQ-11)

- **Actor/Persona**: ผู้ใช้ประจำที่ใช้แอปมาระยะหนึ่งแล้วและมี log สะสม
- **Goal**: อยากรู้ว่าจะถึงน้ำหนักเป้าหมายเมื่อไหร่ เพื่อประเมินความคืบหน้า
- **Trigger**: ผู้ใช้เปิดหน้า Progress/Insights
- **Preconditions**: มีน้ำหนักเป้าหมาย (target weight — กรอกที่ ONB-3: บังคับเมื่อเลือก "ลดน้ำหนัก"
  ไม่บังคับสำหรับเป้าหมายอื่น) และมีประวัติ log แคลอรี่จริงสะสมพอสมควร (PLN-3)
- **Success State**: ผู้ใช้เห็นวันที่คาดว่าจะถึงเป้าหมายน้ำหนัก คำนวณจากอัตราขาดดุลแคลอรี่เฉลี่ยที่บันทึกจริง
  โดยใช้ค่าคงที่ 7,700 kcal ≈ 1 กก. (REQ-11)
- **Alt/Edge Cases**:
  - ผู้ใช้ยังไม่มีน้ำหนักเป้าหมายบันทึกไว้ (เช่น เลือกเป้าหมาย "กระชับสัดส่วน"/"เพิ่มความอึด" แล้วข้ามช่อง
    ไม่บังคับใน ONB-3) → ระบบแจ้งว่ายังพยากรณ์ไม่ได้ ต้องไปกรอกน้ำหนักเป้าหมายก่อน
  - มีประวัติ log ไม่เพียงพอ (เช่น เพิ่งเริ่มใช้แอป) → ระบบแจ้งว่ายังพยากรณ์ไม่ได้ ต้องสะสมข้อมูลเพิ่ม —
    จำนวนวัน log ขั้นต่ำที่ชัดเจนก่อนเริ่มพยากรณ์ได้ยังไม่ระบุ (ดู Open Questions)
  - อัตราขาดดุลเฉลี่ยเป็น 0 หรือสวนทางเป้าหมาย → แสดงข้อความแจ้งเตือนแทนวันที่คาดการณ์

### INT-2 — ซิงค์ตาชั่งอัจฉริยะ (REQ-12)

> **Precondition**: flow นี้เริ่มหลังผ่าน [INT-0 — ยืนยันตัวตนก่อนจับคู่อุปกรณ์ผ่านรหัสจับคู่](#int-0--ยืนยันตัวตนก่อนจับคู่อุปกรณ์ผ่านรหัสจับคู่-req-18)
> สำเร็จแล้วเสมอ (มือถือได้รับ session ที่ authenticated ผูกกับบัญชีจากเว็บ ONB-0) — ดูขั้นตอนเต็มของ INT-0
> แยกต่างหาก ไม่ duplicate ซ้ำที่นี่อีกแล้วตั้งแต่ 2026-08-30

```mermaid
flowchart TD
    A[จับคู่ตาชั่งอัจฉริยะ] --> B[ผู้ใช้ชั่งน้ำหนัก]
    B --> C{เชื่อมต่อสำเร็จ?}
    C -- ไม่ --> D[fallback: กรอกน้ำหนักเอง]
    C -- ใช่ --> E[ซิงค์น้ำหนัก/องค์ประกอบร่างกายเข้าโปรไฟล์]
```

**คำอธิบายตามลำดับ diagram:**

   [INT-0](#int-0--ยืนยันตัวตนก่อนจับคู่อุปกรณ์ผ่านรหัสจับคู่-req-18) สำเร็จแล้ว (REQ-12)
2. ผู้ใช้ชั่งน้ำหนัก ตาชั่งส่งค่าน้ำหนัก/องค์ประกอบร่างกายมาที่แอป (REQ-12)
3. ถ้าการเชื่อมต่อไม่สำเร็จ → fallback ให้ผู้ใช้กรอกน้ำหนักเอง (REQ-12)
4. ถ้าเชื่อมต่อสำเร็จ → ระบบซิงค์ค่าน้ำหนักล่าสุดเข้าโปรไฟล์ผู้ใช้ทันทีโดยไม่ต้องกรอกเอง (REQ-12)
5. ค่าน้ำหนักใหม่ถูกใช้คำนวณ TDEE ใหม่ (ONB-1), แคลอรี่เผาผลาญ (REC-2), และพยากรณ์เป้าหมาย (INT-1) (REQ-12)

- **Actor/Persona**: ผู้ใช้ประจำที่มีตาชั่งอัจฉริยะ (smart scale) และมีบัญชีผู้ใช้จากเว็บแอปอยู่แล้ว (ONB-0)
- **Goal**: ไม่ต้องกรอกน้ำหนักเอง อยากให้ระบบอัปเดตอัตโนมัติและแม่นยำ
- **Trigger**: ผู้ใช้ผ่าน [INT-0](#int-0--ยืนยันตัวตนก่อนจับคู่อุปกรณ์ผ่านรหัสจับคู่-req-18) สำเร็จแล้วต้องการ
  เชื่อมต่อ/จับคู่ตาชั่งอัจฉริยะ แล้วขึ้นชั่งน้ำหนัก
- **Preconditions**: ผ่าน [INT-0](#int-0--ยืนยันตัวตนก่อนจับคู่อุปกรณ์ผ่านรหัสจับคู่-req-18) สำเร็จแล้ว
  (มือถือมี session ที่ authenticated ผูกกับบัญชีจากเว็บ ONB-0) และมีตาชั่งอัจฉริยะที่รองรับ Bluetooth
  หรือ Health API
- **Success State**: น้ำหนัก/องค์ประกอบร่างกายอัปเดตอัตโนมัติในโปรไฟล์ทุกครั้งที่ชั่ง โดยไม่ต้องกรอกมือ (REQ-12)
- **Alt/Edge Cases**:
  - ยังไม่ผ่าน [INT-0](#int-0--ยืนยันตัวตนก่อนจับคู่อุปกรณ์ผ่านรหัสจับคู่-req-18) (เช่น รหัสจับคู่หมดอายุ/
    ถูกใช้ไปแล้ว หรือยังไม่มีบัญชีจากเว็บมาก่อนเลย) → ใช้ feature นี้ไม่ได้เลย ดู Alt/Edge Cases ของ INT-0
  - การเชื่อมต่อ Bluetooth/Health API ขาดหาย → ตกกลับไปให้ผู้ใช้กรอกน้ำหนักเอง
  - มีค่าน้ำหนักหลายค่าในวันเดียว (ชั่งหลายรอบ) → ใช้ค่าล่าสุด หรือค่าเฉลี่ยของวันนั้น ยังไม่ระบุชัดเจน (ดู Open Questions)

### INT-3 — ซิงค์ข้อมูล Wearable (REQ-13)

> **Precondition**: flow นี้เริ่มหลังผ่าน [INT-0 — ยืนยันตัวตนก่อนจับคู่อุปกรณ์ผ่านรหัสจับคู่](#int-0--ยืนยันตัวตนก่อนจับคู่อุปกรณ์ผ่านรหัสจับคู่-req-18)
> สำเร็จแล้วเสมอ (มือถือได้รับ session ที่ authenticated ผูกกับบัญชีจากเว็บ ONB-0) — ดูขั้นตอนเต็มของ INT-0
> แยกต่างหาก ไม่ duplicate ซ้ำที่นี่อีกแล้วตั้งแต่ 2026-08-30

```mermaid
flowchart TD
    A[เชื่อมต่อ Wearable ผ่าน Health API] --> B[ออกกำลังกาย]
    B --> C{มีข้อมูลแคลอรี่จาก Wearable?}
    C -- มี --> D[ใช้ค่าจาก Wearable แทนค่าประมาณ MET]
    C -- ไม่มี --> E[ใช้ค่าประมาณจากสูตร MET REC-2]
    D --> F[บันทึก log ด้วยค่าที่แม่นยำขึ้น]
    E --> F
```

**คำอธิบายตามลำดับ diagram:**

1. ผู้ใช้อนุญาตแอปมือถือให้เข้าถึงข้อมูลจาก Apple Health/Google Health Connect เพื่อเชื่อมต่อ wearable —
   หลังผ่าน [INT-0](#int-0--ยืนยันตัวตนก่อนจับคู่อุปกรณ์ผ่านรหัสจับคู่-req-18) สำเร็จแล้ว (REQ-13)
2. ผู้ใช้ออกกำลังกาย ระหว่าง/หลังนั้น wearable บันทึกแคลอรี่ที่เผาผลาญจริงจากอัตราการเต้นหัวใจและกิจกรรม (REQ-13)
3. ถ้ามีข้อมูลแคลอรี่จาก wearable → แอปดึงค่านั้นมาแทนที่ค่าประมาณจากสูตร MET ที่คำนวณจาก REC-2 (REQ-13)
4. ถ้าไม่มีข้อมูลจาก wearable → ใช้ค่าประมาณจากสูตร MET ของ REC-2 แทนชั่วคราว (REQ-13)
5. ค่าที่ได้ (จาก wearable หรือค่าประมาณ) ถูกใช้ในการบันทึก log (PLN-3) และคำนวณอื่น ๆ ที่เกี่ยวข้อง เช่น
   การพยากรณ์ (INT-1) (REQ-13)

- **Actor/Persona**: ผู้ใช้ประจำที่มี Apple Watch/Fitbit/Garmin และมีบัญชีผู้ใช้จากเว็บแอปอยู่แล้ว (ONB-0)
- **Goal**: ให้ค่าแคลอรี่ที่เผาผลาญแม่นยำขึ้นกว่าค่าประมาณจากสูตร MET
- **Trigger**: ผู้ใช้ผ่าน [INT-0](#int-0--ยืนยันตัวตนก่อนจับคู่อุปกรณ์ผ่านรหัสจับคู่-req-18) สำเร็จแล้วต้องการ
  เชื่อมต่อ wearable ผ่าน Apple Health หรือ Google Health Connect แล้วออกกำลังกาย
- **Preconditions**: ผ่าน [INT-0](#int-0--ยืนยันตัวตนก่อนจับคู่อุปกรณ์ผ่านรหัสจับคู่-req-18) สำเร็จแล้ว
  (มือถือมี session ที่ authenticated ผูกกับบัญชีจากเว็บ ONB-0) และมี wearable ที่รองรับและเชื่อมต่อกับ
  Apple Health/Google Health Connect แล้ว
- **Success State**: แคลอรี่ที่บันทึกในระบบมาจาก wearable แทนค่าประมาณจากสูตร MET เมื่อมีข้อมูลพร้อม (REQ-13)
- **Alt/Edge Cases**:
  - ยังไม่ผ่าน [INT-0](#int-0--ยืนยันตัวตนก่อนจับคู่อุปกรณ์ผ่านรหัสจับคู่-req-18) (เช่น รหัสจับคู่หมดอายุ/
    ถูกใช้ไปแล้ว หรือยังไม่มีบัญชีจากเว็บมาก่อนเลย) → ใช้ feature นี้ไม่ได้เลย ดู Alt/Edge Cases ของ INT-0
  - Wearable ไม่ได้เชื่อมต่อ หรือข้อมูลมาช้า/ไม่ครบ → ใช้ค่าประมาณจากสูตร MET (REC-2) แทนชั่วคราว
  - ค่าจาก wearable กับค่าประมาณจากสูตร MET ต่างกันมาก → ยังไม่ระบุวิธีจัดการความขัดแย้ง (ดู Open Questions)

## Open Questions

ทุกข้อ REQ-01 ถึง REQ-18 มี feature รองรับครบแล้ว (REQ-14–17 เพิ่มเข้า Onboarding & Personalization
spec เมื่อ 2026-08-29 ครอบคลุมโดย [ONB-0](#onb-0--สมัครสมาชิก--เข้าสู่ระบบ--ลืมรหัสผ่าน--ออกจากระบบ-req-14-req-15-req-16-req-17)
ด้านบน; REQ-18 เพิ่มเข้า Smart Integrations spec เมื่อ 2026-08-30 ครอบคลุมโดย
[INT-0](#int-0--ยืนยันตัวตนก่อนจับคู่อุปกรณ์ผ่านรหัสจับคู่-req-18) ด้านบน — ดู
[REQ Traceability Matrix](../../01-requirements/backlog.md#req-traceability-matrix)) 5 จุดที่เคยเป็นความไม่ชัดเจนซึ่ง
กระทบโครงสร้าง journey ของ feature ระดับ Must/Should อย่างมีนัยสำคัญ (ONB-3/REQ-02, REC-2/REQ-05,
PLN-2/REQ-09, PLN-3-PLN-4/REQ-10, และ PLN-1/REQ-08 เรื่องนิยาม "ปฏิทินรายสัปดาห์" ที่ resolve เพิ่มเมื่อ
2026-08-27) ได้ถูกนำไปถามผู้ใช้งานและ **resolve แล้ว** ตามส่วน
"ข้อสมมติฐาน/การตัดสินใจที่ยืนยันแล้ว" ของเอกสาร
[Onboarding](../../01-requirements/01-spec/20260823-01-onboarding-personalization.md),
[Daily YouTube Recommendation](../../01-requirements/01-spec/20260823-02-daily-youtube-recommendation.md) และ
[Planner & Logging](../../01-requirements/01-spec/20260823-03-planner-logging.md)
— ถูก bake เข้า Steps/diagram ด้านบนแล้ว ไม่ใช่ Open Question อีกต่อไป

รายการที่เหลือด้านล่างเป็นรายละเอียดเชิง implementation ปลีกย่อยที่ **ไม่กระทบโครงสร้าง journey ของ
feature ระดับ Must/Should อย่างมีนัยสำคัญ** (ตามเกณฑ์ใน SKILL.md) จึงยังคงบันทึกไว้เป็น Open Questions
รอทีม product ตัดสินใจเพิ่มเติม แทนที่จะเดาไว้ใน Steps ข้างต้น:

1. **REC-1 (REQ-04)**: ไม่ได้ระบุ tolerance ว่าวิดีโอต้องใกล้เคียงเป้าหมายแคลอรี่แค่ไหนถึงเรียกว่า "ตรงกัน"
   และไม่ได้ระบุว่ารองรับการแนะนำวิดีโอหลายคลิปรวมกันให้ถึงเป้าหมายหรือไม่
2. **REC-4 (REQ-07)**: ไม่ได้ระบุว่าเวลา/แคลอรี่ของวอร์มอัพ-คูลดาวน์นับรวมในเป้าหมายรายวันหรือไม่
3. **INT-1 (REQ-11)**: ไม่ได้ระบุจำนวนวัน log ขั้นต่ำก่อนเริ่มพยากรณ์ได้ (ค่าคงที่ 7,700 kcal ≈ 1 กก.
   ได้ resolve แล้วใน decision ของ ONB-3/REQ-02)
4. **INT-2/INT-3 (REQ-12, REQ-13)**: ไม่ได้ระบุลำดับความสำคัญเมื่อมีข้อมูลชนกัน (เช่น ชั่งน้ำหนักหลายครั้ง
   ต่อวันจากตาชั่งอัจฉริยะ ควรใช้ค่าล่าสุดหรือค่าเฉลี่ย หรือค่าจาก wearable ต่างจากค่าประมาณจากสูตร MET
   มากควรจัดการอย่างไร)
5. **ONB-0 (REQ-14)**: ยังไม่ได้ระบุว่าต้องมีขั้นตอนยืนยันอีเมล (email verification) ก่อนใช้งานได้จริงหรือไม่
   และยังไม่ได้ระบุกติกาความซับซ้อนของรหัสผ่าน (password policy) สำหรับ email/password
6. **ONB-0 (REQ-15)**: ยังไม่ได้ระบุระยะเวลาหมดอายุของ session (session timeout) ที่แน่นอน
7. **INT-0 (REQ-18)**: ยังไม่ได้ระบุกติกา rate limiting เมื่อผู้ใช้กรอกรหัสจับคู่ผิดซ้ำ ๆ หลายครั้งติดกัน
   บนมือถือ (เช่น ควร lock ชั่วคราวหลังกี่ครั้ง) — รายละเอียด implementation ปลีกย่อยที่ไม่กระทบโครงสร้าง
   journey เพราะ INT-0 เป็น Could-priority

> **PLN-1 (REQ-08) — resolve แล้วเมื่อ 2026-08-27** (เดิมเป็นข้อ 3 ในลิสต์นี้): ทั้งสองจุด — (1) นิยามของ
> "ปฏิทินรายสัปดาห์" (fixed calendar week จันทร์–อาทิตย์ ไม่ใช่ rolling 7-day-forward window) และ
> (2) ผู้ใช้แก้ไขแผนของวันที่ผ่านไปแล้ว (มี log แล้ว) ได้หรือไม่ (คำตอบ = ไม่ได้ read-only เท่านั้น) —
> ถูกยืนยันจากผู้ใช้งานแล้ว ดูรายละเอียดที่
> [Planner spec § ข้อสมมติฐาน/การตัดสินใจที่ยืนยันแล้ว](../../01-requirements/01-spec/20260823-03-planner-logging.md#ข้อสมมติฐานการตัดสินใจที่ยืนยันแล้ว)
> และ bake เข้า Steps/diagram ของ PLN-1 ด้านบนแล้ว ไม่ใช่ Open Question อีกต่อไป
