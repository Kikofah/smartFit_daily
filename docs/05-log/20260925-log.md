## Implement งานค้างจาก `spec.md` §6.3 ด้วยผู้ช่วย 3 ตัว (INT-2/INT-3 มือถือ, unit test, pairing security)

**บริบท**: ผู้ใช้อนุมัติแผนแบ่งงานให้ผู้ช่วย 3 ตัว (Sonnet 5 ทั้งหมด — ผู้ช่วย C เดิมวางไว้เป็น Haiku แต่เปลี่ยนเมื่อพบว่า
ต้อง refactor ก่อนเขียน test) โดย session หลักทำหน้าที่ review/verify/commit

**การตัดสินใจที่ผู้ใช้ยืนยันแล้ว (ยังต้องบันทึกลง `01-spec/20260823-04-smart-integrations.md` ผ่าน `feature-list-journey`)**:

- **INT-0 / REQ-18 rate limit**: กรอกรหัสจับคู่ผิด 5 ครั้งภายใน 15 นาที (ต่อ IP) → 429 จนหมดหน้าต่างเวลา
- **INT-0 / REQ-18 รหัสต่อบัญชี**: มีรหัสที่ใช้งานได้ทีละ 1 รหัส — สร้างใหม่แล้วรหัสเก่าถูกยกเลิก
- **INT-2/INT-3 ข้อมูลชนกัน**: ทำ happy path ก่อน (ส่งทุกค่าตามเดิม) — ยังเป็น open point

**สิ่งที่ทำ**:

1. **A — มือถือ INT-2/INT-3** (`apps/mobile/`): consent ก่อนเชื่อมต่อ (NFR-05), BLE Weight Scale Service
   (0x181D/0x2A9D), HealthKit/Health Connect permission + `connect`, ย้าย Firebase config ไป `app.config.js`
   `extra` — ยังไม่ได้ทดสอบบนเครื่องจริง (ต้องใช้ EAS Development Build)
2. **C — unit test** (`apps/web/server/domain/`): ดึงสูตร TDEE, goal/safety floor, MET, all-or-nothing log,
   streak, forecast, warmup/cooldown ออกเป็น pure function (ไม่เปลี่ยนค่าที่คำนวณ) + Vitest 2
3. **B — pairing security**: rate limit เก็บใน Firestore (`pairingRedeemAttempts/{sha256(ip)}`) ภายใต้
   transaction, 1 รหัสต่อบัญชี, แก้ bug เดิม 3 จุด (รหัสชนกันเขียนทับของผู้อื่น → `.create()`+retry,
   redeem ซ้ำพร้อมกันได้ → transaction, 999999 สุ่มไม่ได้), Firestore rules เป็น deny-all (client ไม่ใช้
   Firestore SDK เลย ทุกอย่างผ่าน Admin SDK)
4. **Review โดย session หลัก**: พบว่า `trust proxy: true` ทำให้ rate limit ถูกเลี่ยงได้ด้วยการปลอม
   `X-Forwarded-For` — แก้เป็น hop count (`TRUST_PROXY_HOPS`, ค่าเริ่มต้น 1 = ปลอมไม่ได้ แต่ผู้ใช้หลัง
   Firebase Hosting อาจแชร์ bucket เดียวกัน) + log วินิจฉัย `LOG_FORWARDED_FOR=1` ชั่วคราว

**ผล**: test 50/50 ผ่าน (3 ตัวเป็น `it.fails` โดยตั้งใจ), typecheck/lint ผ่านทั้ง monorepo

**ยังค้าง / ต้องตัดสินใจ**:

index.ts`, `routes/personalization-profile/index.ts`, `domain/goalTargets.ts`) ก่อนแก้ — ไม่มีเครื่องมือ
ถามผู้ใช้แบบ interactive ใน subagent นี้ จึงตัดสินใจตามที่ skill แนะนำแล้วรายงานกลับให้ผู้ใช้ตรวจสอบแทนตาม
ที่ระบุไว้ในคำสั่งงาน

**แก้ไข `detailed-design/04-smart-integrations.md`**:

- **INT-0**: เพิ่มขั้นตอนตรวจสอบตัวนับ `pairing_redeem_rate_limit` (§3.20) **ก่อน**แม้แต่จะตรวจรหัสที่ส่งมา
  พร้อม `alt` ใหม่ `429`+`Retry-After` เมื่อถูกล็อก, เพิ่มขั้นตอน invalidate รหัสเก่าทั้งหมดของบัญชีเดียวกัน
  ตอน mint (one-live-code-per-account), ระบุว่า lookup+delete ของรหัส/ตัวนับเกิดขึ้นแบบ atomic (ธุรกรรม
  เดียวกัน) — เพิ่ม**อัลกอริทึมใหม่ "ตรวจสอบ Rate Limit การแลกรหัสจับคู่"** (ไม่เคยมีมาก่อน)
- **INT-3**: เขียน sequence diagram ใหม่ทั้งหมด — จบ session ที่เว็บ Planner ก่อนเสมอ (companion app ไม่มี
  หน้าจอบันทึกการออกกำลังกายของตัวเอง) → มือถือกด "ซิงค์" เรียก `GET /integrations/wearable/latest-session`
  หา session ล่าสุดใน 24 ชม. → `alt` 3 กรณี (`404` ไม่พบ / กำลังดำเนินอยู่ / จบแล้ว) → อ่าน Active Calories
  เฉพาะช่วงเวลา session → `POST /integrations/wearable/readings` → `alt` แยก pre-complete (path เดิม) กับ
  retroactive correction (session ปิดจบแล้ว → แก้ `daily_log` ด้วย**ส่วนต่าง (delta)** ผ่าน Logging & Streak
  → recompute completion/streak ทันที) — เพิ่ม**อัลกอริทึมใหม่ "แก้ไข Daily Log ย้อนหลังด้วยส่วนต่าง (Delta)
  เมื่อซิงค์ Wearable หลัง Session ปิดจบแล้ว"** (ไม่เคยมีมาก่อน — เดิม INT-3 เป็น fallback flow ตรงไปตรงมา
  ไม่มี algorithm section)
- อัปเดต "จุดที่ยังไม่ได้ระบุ" (ยืนยัน happy-path only ของ INT-2/INT-3 ตาม decision 2026-09-25) และ
  "ความสัมพันธ์กับเอกสารอื่น" (เพิ่มตาราง `pairing_redeem_rate_limit`, operation `GET .../latest-session`,
  column `workout_session.log_date`)
- ภาคผนวก Stack Mapping: เพิ่มหมายเหตุ freshness ว่า `tech-stack.md` §6.1/§6.3.1 (ฉบับ 2026-08-31) ยังไม่มี
  mapping ของ rate-limit/one-live-code/`latest-session` เลย — ไม่แก้ตาราง mapping เอง (ยังคง mirror
  เนื้อหาปัจจุบันของ `tech-stack.md` ตรงตัว) แนะนำรัน `tech-stack-builder` ต่อ

**แก้ไข `detailed-design/01-onboarding-personalization.md`**:

- **ONB-3**: เขียน sequence diagram ใหม่ — ตัด `par` block เดิมที่ client คำนวณทั้งสองค่าแล้วส่งเป็นค่าที่
  เชื่อถือได้ออก (เหลือแค่คำนวณตัวอย่าง/preview เพื่อแสดงผล), request เหลือแค่ประเภทเป้าหมาย+น้ำหนักเป้าหมาย,
  เพิ่ม `alt` ใหม่ `409` เมื่อยังไม่ทำ ONB-1, server อ่านน้ำหนักตัว/TDEE จากโปรไฟล์เองแล้วคำนวณทั้งสองค่า+
  safety floor เองทั้งหมด (server-authoritative, ไม่เชื่อ legacy field จาก client), response เปลี่ยนเป็น
  `204` (ต้องเรียก `GET /profile` แยกเพื่ออ่านค่าจริง) — เขียนอัลกอริทึกใหม่ตามโมเดล server-authoritative นี้
  พร้อมย้ำ 2 กติกา: ค่าที่แม่นยำไม่ปัดเศษ และ safety floor เข้มงวดที่ต่ำกว่า 1,200 kcal **อย่างเคร่งครัด**
  (เท่ากับ 1,200 พอดี → ไม่ถูกปรับ)
- อัปเดต "จุดที่ยังไม่ได้ระบุ" ข้อ safety floor ให้ระบุว่า boundary rule resolve แล้ว (ตัวเลขสุดท้ายในช่วง
  1,200–1,500 เองยังคงเป็น open point เดิม) และ "ความสัมพันธ์กับเอกสารอื่น" (อ้าง `409`/`204` ใหม่)
- ภาคผนวก Stack Mapping: เพิ่มหมายเหตุ freshness ว่า `tech-stack.md` §6.1 (ฉบับ 2026-08-31) ยังอธิบายโมเดล
  เดิม "client คำนวณ + server re-derive safety floor ซ้ำ" ไม่ตรงกับ server-authoritative ใหม่ — ไม่แก้ตาราง/
  ย่อหน้า Execution เอง (ยัง mirror `tech-stack.md` ตรงตัว) แนะนำรัน `tech-stack-builder` ต่อ

**การตัดสินใจที่ทำแทนผู้ใช้ (ไม่มีจุดที่ต้องเลือกจริงๆ — เป็น mechanical derive จาก decision ที่ resolve
แล้วทั้งหมด)**: (1) เพิ่ม algorithm section ใหม่ให้ INT-0 และ INT-3 (เดิมทั้งคู่ไม่มี เพราะเคยเป็น flow
ตรงไปตรงมา) ตามที่คำสั่งงานแนะนำไว้ตรงๆ ว่า "Consider a small algorithm write-up"/"Update the algorithm
write-up" — ยึดตามคำแนะนำนั้น (2) คงเป็น sequence diagram เดียวต่อ Feature ID (ไม่แตกเป็นหลายไดอะแกรมย่อย)
สำหรับทั้ง INT-0 (เพิ่ม `alt` ซ้อน) และ INT-3 (เพิ่ม `alt` ใหม่ 2 ชั้น) เพราะยังอยู่ในขอบเขตที่อ่านง่าย
เทียบเท่ากับ INT-2 ที่มีอยู่แล้วในไฟล์เดียวกัน ไม่ถึงเกณฑ์ที่ต้องแยกตามที่ skill แนะนำเรื่องความซับซ้อนเกิน
(3) เลือก**ไม่แก้ตาราง Stack Mapping ของทั้งสองไฟล์** แม้เนื้อหาหลักจะเปลี่ยนไปมาก เพราะ `tech-stack.md`
เองยังไม่ sync — ยึดกติกา "มิเรอร์ ไม่ใช่แก้ไข" อย่างเคร่งครัด เพิ่มได้แค่หมายเหตุ freshness ตาม pattern ที่
ไฟล์เหล่านี้เคยใช้มาก่อนหน้านี้ (เช่น INT-1 forecast, PLN-4 streak) ไม่ใช่การตัดสินใจใหม่

**สิ่งที่พบว่า upstream ไม่สอดคล้องกัน**: ไม่มี — `01-spec/`, `backlog.md`, `user-journeys.md`, `api-spec.md`,
`database-schema.md` ทั้งหมดสอดคล้องกันดีอยู่แล้วสำหรับ 3 Feature ID นี้ (ตรวจสอบตรงกับโค้ดจริงทุกจุดที่อ้าง)
— มีเพียง `tech-stack.md` ที่ล้าหลัง (เป็น "เอกสารล้าหลัง" ธรรมดา ไม่ใช่ข้อขัดแย้ง) ตามที่ระบุไว้ในภาคผนวก
Stack Mapping ของทั้งสองไฟล์ข้างต้น

**ไม่มีคำถามค้างสำหรับผู้ใช้** — ทุกจุดที่แก้ไข derive ตรงจาก decision ที่ resolve แล้วใน upstream ทั้งหมด
ไม่มี edge case ใหม่ที่ต้องเดา
