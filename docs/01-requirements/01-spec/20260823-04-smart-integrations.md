- **ประเภท:** Feature
- **สถานะเอกสาร:** Draft

## ขอบเขต (Scope)

**อยู่ในขอบเขต (In scope)**

- ยืนยันตัวตนผู้ใช้บนมือถือก่อนจับคู่อุปกรณ์ ผ่านกลไกรหัสจับคู่ (pairing code) — เพิ่มเข้าขอบเขตเป็นทางการ
  2026-08-30 (ดู REQ-18 ด้านล่าง)
- พยากรณ์วันที่คาดว่าจะถึงน้ำหนักเป้าหมาย
- ซิงค์น้ำหนัก/องค์ประกอบร่างกายจากตาชั่งอัจฉริยะ
- ซิงค์ข้อมูลจาก wearable (Apple Watch / Fitbit / Garmin)

**นอกขอบเขต (Out of scope)**

- ยังไม่ได้ระบุไว้ในเอกสารต้นฉบับ (product backlog เดิม)

## รายละเอียด (Description)

ชุด feature เสริมที่เพิ่มความแม่นยำและ insight ให้ผู้ใช้ที่ใช้แอปมาระยะหนึ่งแล้ว ไม่ใช่เงื่อนไขที่ core loop
รายวัน (Onboarding → Recommendation → Logging) ต้องพึ่งพา ฟีเจอร์ insight/sync ทั้งสาม (INT-1/INT-2/INT-3)
จึงเป็น MoSCoW = Could — ส่วน REQ-18 (กลไกยืนยันตัวตนก่อนจับคู่อุปกรณ์) แม้เป็น Could เช่นกัน (เพราะมีอยู่เพื่อ
รองรับ INT-2/INT-3 เท่านั้น ไม่มี feature อื่นที่เป็น Must/Should พึ่งพา) แต่เป็น **precondition ทางเทคนิคร่วม**
ที่ INT-2/INT-3 ทั้งคู่ต้องผ่านก่อนจึงจะทำงานได้จริงบนมือถือ (companion app ไม่มีหน้าจอ auth ของตัวเอง — ดู
[Onboarding spec § ONB-0](20260823-01-onboarding-personalization.md#ข้อสมมติฐานการตัดสินใจที่ยืนยันแล้ว))

## เงื่อนไข/กติกาทางธุรกิจ (Business Rules)

1. **REQ-11**: คำนวณวันที่คาดว่าจะถึงน้ำหนักเป้าหมาย จากอัตราขาดดุลแคลอรี่เฉลี่ยที่บันทึกจริง
2. **REQ-12**: ซิงค์น้ำหนัก/องค์ประกอบร่างกายจากตาชั่งอัจฉริยะผ่าน Bluetooth หรือ Health API
3. **REQ-13**: ดึงแคลอรี่เผาผลาญจริงจาก Apple Health/Google Health Connect มาทดแทนค่าที่ระบบประมาณจากวิดีโอ
4. **REQ-18** (ใหม่ 2026-08-30): การยืนยันตัวตนก่อนจับคู่อุปกรณ์ผ่านรหัสจับคู่ (Pairing Code) — ผู้ใช้ที่
   ล็อกอินอยู่บนเว็บแอปแล้ว (ONB-0) ขอรหัสจับคู่อุปกรณ์แบบตัวเลข 6 หลักจากหน้าโปรไฟล์ ระบบ (server) เป็น
   ผู้สร้างรหัสนี้ผูกกับบัญชีผู้ใช้ที่ล็อกอินอยู่ขณะนั้นเสมอ รหัสมีอายุการใช้งาน **5 นาที** และเป็น
   **single-use** (ใช้ซ้ำไม่ได้หลัง redeem สำเร็จหรือหมดอายุ) ผู้ใช้กรอกรหัสนี้บน companion mobile app
   เพื่อแลกเป็น session ที่ authenticated แบบ silent (sign in โดยไม่ต้องกรอก credential ซ้ำ) ผูกกับบัญชี
   เดิมที่สร้างรหัสไว้ ก่อนเข้าสู่หน้าจับคู่อุปกรณ์จริง (INT-2/INT-3) — กติกา rate limit เมื่อกรอกรหัสผิดซ้ำ
   และกติกา "1 บัญชีมีรหัสที่ใช้งานได้ทีละ 1 รหัส" resolve แล้วเมื่อ 2026-09-25 (ดู "ข้อสมมติฐาน/การตัดสินใจ
   ที่ยืนยันแล้ว" ด้านล่าง)

[Onboarding/ONB-3 (REQ-02)](20260823-01-onboarding-personalization.md#ข้อสมมติฐานการตัดสินใจที่ยืนยันแล้ว)

  ของตัวเอง (INT-0) — ยืนยันกับผู้ใช้งานแล้ว 2026-08-30**: เดิมบันทึกไว้เป็น "จุดที่ยังไม่ได้ระบุ" ว่าควรมี
  REQ number ของตัวเองหรือไม่ (ดู codebase 2026-08-30) ผู้ใช้งานยืนยันให้ (ก) ตั้งเป็น **REQ-18** ใหม่
  (ดู "เงื่อนไข/กติกาทางธุรกิจ" ด้านบน) และ (ข) ให้ Feature ID ของตัวเอง คือ **INT-0** ผูกกับ Epic Smart
  Integrations (ไม่ใช่ Onboarding) — โดยตั้งชื่อ/จัดวางตามแบบแผนเดียวกับที่ **ONB-0** เคยได้รับ Feature ID
  ของตัวเองมาก่อนแล้ว ในฐานะ foundational precondition ที่ feature อื่นในกลุ่มเดียวกันใช้ร่วมกัน (ONB-0 เป็น
  precondition ของทั้งแอป; INT-0 เป็น precondition เฉพาะของ INT-2/INT-3 เท่านั้น) เหตุผลที่ผูกกับ Smart
  Integrations แทน Onboarding: กลไกนี้เกิดขึ้นเฉพาะตอนผู้ใช้ต้องการจับคู่อุปกรณ์ (INT-2/INT-3) เท่านั้น
  ไม่ใช่ส่วนหนึ่งของ flow onboarding บนเว็บที่ ONB-0/1/2/3 ครอบคลุมอยู่แล้ว

  กลไกที่ implement จริงในโค้ดมีดังนี้ (อ้างอิงเดิมจาก codebase 2026-08-30):
  1. ผู้ใช้ที่ล็อกอินอยู่แล้วบนเว็บแอป (จาก ONB-0) เปิดหน้าโปรไฟล์ กดขอรหัสจับคู่อุปกรณ์ → server สร้างรหัส
     จับคู่ 6 หลัก อายุการใช้งาน 5 นาที แสดงบนหน้าจอเว็บ
  2. ผู้ใช้เปิด companion app บนมือถือ กรอกรหัส 6 หลักนั้น → server ตรวจสอบรหัส (ถูกต้อง/ยังไม่หมดอายุ/
     ยังไม่ถูกใช้ — single-use) แล้ว mint short-lived token ผูกกับบัญชีผู้ใช้เดิมที่สร้างรหัสไว้
  3. มือถือใช้ token นั้นเข้าสู่ระบบแบบ silent (ไม่ต้องกรอกรหัสผ่านซ้ำ) แล้วเข้าสู่หน้าจับคู่อุปกรณ์จริง
     (INT-2/INT-3 UI)

  REQ-18/INT-0 เป็น **precondition ทางเทคนิคร่วม** ของ INT-2 และ INT-3 ทั้งคู่ ไม่ใช่ส่วนหนึ่งของเนื้อหา
  business rule ของ REQ-12/REQ-13 เอง (ซึ่งยังคงเนื้อหาเดิมไม่เปลี่ยนแปลง) — ในเอกสาร
  [user-journeys.md](../../02-design/01-prototypes/user-journeys.md) ขั้นตอนเหล่านี้ถูกแยกเป็น entry ของ
  ตัวเอง (INT-0) แล้ว โดย INT-2/INT-3 อ้างอิงกลับมาเป็น precondition แทนการ duplicate ขั้นตอนซ้ำเหมือนก่อน
  หน้านี้

- **INT-0/REQ-18 — กติกา rate limit เมื่อกรอกรหัสจับคู่ผิดซ้ำ (ยืนยันกับผู้ใช้งานแล้ว 2026-09-25, resolve
  จุดที่เคยเป็น "จุดที่ยังไม่ได้ระบุ")**: กรอกรหัสผิด **5 ครั้งภายในหน้าต่างเวลา 15 นาที ต่อ client IP
  เดียวกัน** → ถูกล็อกชั่วคราว (ตอบ `HTTP 429` พร้อม header `Retry-After`) จนกว่าหน้าต่างเวลาจะหมดอายุ
  client ที่ถูกล็อกอยู่จะถูกปฏิเสธ**ก่อน**แม้แต่จะตรวจสอบรหัสที่กรอกมาด้วยซ้ำ (ป้องกันการ probe รหัสต่อขณะ
  ยังล็อกอยู่) และ redeem ที่**สำเร็จ**จะรีเซ็ตตัวนับของ client นั้นทันที — implement จริงแล้วที่
  `POST /api/pairing/redeem` (`apps/web/server/routes/pairing/index.ts`, นับ attempt ต่อ hash ของ IP
  เก็บใน Firestore ภายใต้ transaction เดียวกับการตรวจ/ลบรหัส เพื่อกันการ race แข่งผ่าน threshold พร้อมกัน)
- **INT-0/REQ-18 — 1 บัญชีมีรหัสจับคู่ที่ใช้งานได้ทีละ 1 รหัสเท่านั้น (ยืนยันกับผู้ใช้งานแล้ว 2026-09-25)**:
  เมื่อผู้ใช้กดขอรหัสจับคู่ใหม่ (`POST /api/pairing/create-code`) ระบบจะยกเลิกรหัสเก่าที่ยังไม่หมดอายุ/
  ยังไม่ถูกใช้ของบัญชีเดียวกันทั้งหมดก่อนเสมอ (ลบทิ้งจริง ไม่ใช่แค่ทำเครื่องหมาย) เหลือเฉพาะรหัสล่าสุดที่
  ใช้งานได้จริง — ป้องกันไม่ให้รหัสเก่าที่ผู้ใช้ลืมไว้ยังใช้ redeem ได้พร้อมกับรหัสใหม่
- **INT-3/REQ-13 — กลไก sync แคลอรี่จริงจาก wearable กับ session การออกกำลังกาย (ยืนยันกับผู้ใช้งานแล้ว
  2026-09-25)**: เนื่องจาก companion mobile app ไม่มีหน้าจอบันทึกการออกกำลังกาย (workout logging UI) ของ
  ตัวเองเลย (การออกกำลังกาย/จบ session ทำที่หน้าเว็บ Planner ทั้งหมด — PLN-3) กลไก sync จริงจึงเป็นแบบ
  ผู้ใช้กดเอง ไม่ใช่ auto-sync ระหว่างออกกำลังกาย ดังนี้:
  1. ผู้ใช้จบการออกกำลังกาย (session) ที่หน้าเว็บให้เสร็จก่อนเสมอ
  2. บนมือถือ (หลังผ่าน INT-0 และเชื่อมต่อ wearable แล้ว) ผู้ใช้กดปุ่ม "ซิงค์แคลอรี่จากการออกกำลังกาย
     ครั้งล่าสุด" แอปจะขอ session ล่าสุดของผู้ใช้จาก server ที่เริ่มภายใน **24 ชั่วโมงที่ผ่านมา**
     (`GET /integrations/wearable/latest-session`)
  3. ถ้าไม่พบ session ใดเลยในช่วง 24 ชม. → แจ้งผู้ใช้ว่ายังไม่พบการออกกำลังกาย
  4. ถ้าพบ session แต่สถานะยังเป็น **"กำลังดำเนินอยู่" (in progress, ยังไม่จบที่เว็บ)** → แอปแจ้งให้ผู้ใช้
     ไปจบการออกกำลังกายที่หน้าเว็บให้เสร็จก่อน ยังไม่อ่าน/ส่งค่าใดๆ
  5. ถ้า session **จบแล้ว (completed)** → แอปอ่านค่า Active Calories จาก HealthKit/Health Connect เฉพาะ
     ช่วงเวลาของ session นั้นเท่านั้น (`[startedAt, startedAt + ระยะเวลาที่ใช้จริง]`) แล้วส่งค่าไปที่ server
     (`POST /integrations/wearable/readings`)
  6. Server แทนที่ค่าประมาณจากสูตร MET เดิมของ session นั้นด้วยค่าจาก wearable เสมอ (wearable ชนะ MET
     ตาม REQ-13 เดิม) และแก้ไข daily log ของวันนั้น (log ของวันที่ session นั้นถูกบันทึกไว้ ไม่ใช่ "วันนี้"
     เสมอไป เพราะอาจ sync ข้ามเที่ยงคืนได้) ด้วย **ส่วนต่าง (delta)** ระหว่างค่าใหม่กับค่าเดิมที่ session
     นั้นเคยมีส่วนสมทบไว้แล้วเท่านั้น — ไม่ใช่ค่าแบบเต็มจำนวน เพื่อไม่ให้ re-sync ซ้ำนับแคลอรี่ซ้ำ (double
     count) เมื่อวันนั้นอาจมีหลาย session
  7. หลังแก้ไข daily log แล้ว ระบบคำนวณสถานะ "ครบเป้าหมาย/ไม่ครบเป้าหมาย" (PLN-3) และ streak (PLN-4)
     ของวันนั้นใหม่ทันที ให้ตรงกับค่าที่แก้ไขแล้ว
  8. การ sync ซ้ำสำหรับ session เดิม (re-sync) ทำได้เสมอ ไม่ถือเป็น error — เขียนทับค่า wearable reading
     เดิมของ session นั้น และคำนวณ delta ซ้ำตามข้อ 6 ทุกครั้ง
- **INT-1/REQ-11 — จำนวนวัน log ขั้นต่ำก่อนเริ่มพยากรณ์ได้ = 7 วัน (ยืนยันกับผู้ใช้งานแล้ว 2026-09-26, resolve
  จุดที่เคยเป็น "จุดที่ยังไม่ได้ระบุ")**: ระบบจะแสดงวันที่คาดว่าจะถึงน้ำหนักเป้าหมายก็ต่อเมื่อผู้ใช้มีประวัติ
  log แคลอรี่ (daily log จาก PLN-3) สะสม **อย่างน้อย 7 วัน** เท่านั้น — ถ้ามีน้อยกว่า 7 วัน ระบบแสดง empty
  state "ประวัติยังไม่พอสำหรับพยากรณ์" แทนวันที่พยากรณ์ (ไม่แสดงวันที่ปลอม/ประมาณการใดๆ) ตัวเลือกที่เสนอ
  ผู้ใช้งาน: 3 วัน (ค่าที่โค้ด hardcode ไว้ชั่วคราวเดิม `MIN_LOG_DAYS_FOR_FORECAST = 3`), 7 วัน, 14 วัน —
  ผู้ใช้งานเลือก **7 วัน** เหตุผล: หนึ่งสัปดาห์เต็มสอดคล้องกับ Weekly Planner แบบคงที่ จันทร์–อาทิตย์ ของ
  [PLN-1](20260823-03-planner-logging.md) ทำให้ค่าเฉลี่ยอัตราขาดดุลครอบคลุมทั้งวันออกกำลังกายและ Rest
  Day/Cheat Day ในสัดส่วนจริงของหนึ่งรอบสัปดาห์ จึงผันผวนน้อยกว่าการเฉลี่ยจากข้อมูลเพียง 3 วัน ขณะที่ยังไม่
  ต้องรอนานเท่า 14 วันก่อนผู้ใช้เห็น insight แรก (โค้ดกำลังปรับค่าคงที่เป็น 7 ให้ตรงกันใน
  `apps/web/server/domain/weightForecast.ts`)
