# 20260823-04 - Smart Integrations

- **ประเภท:** Feature
- **สถานะเอกสาร:** Draft
- **วันที่สร้าง:** 2026-08-23

## ขอบเขต (Scope)

**อยู่ในขอบเขต (In scope)**

- ยืนยันตัวตนผู้ใช้บนมือถือก่อนจับคู่อุปกรณ์ ผ่านกลไกรหัสจับคู่ (pairing code) — เพิ่มเข้าขอบเขตเป็นทางการ
  2026-08-30 (ดู REQ-18 ด้านล่าง)
- พยากรณ์วันที่คาดว่าจะถึงน้ำหนักเป้าหมาย
- ซิงค์น้ำหนัก/องค์ประกอบร่างกายจากตาชั่งอัจฉริยะ
- ซิงค์ข้อมูลจาก wearable (Apple Watch / Fitbit / Garmin)

**นอกขอบเขต (Out of scope)**

- ยังไม่ได้ระบุไว้ในเอกสารต้นฉบับ (product backlog เดิม)

## รายละเอียด (Description)

ชุด feature เสริมที่เพิ่มความแม่นยำและ insight ให้ผู้ใช้ที่ใช้แอปมาระยะหนึ่งแล้ว ไม่ใช่เงื่อนไขที่ core loop
รายวัน (Onboarding → Recommendation → Logging) ต้องพึ่งพา ฟีเจอร์ insight/sync ทั้งสาม (INT-1/INT-2/INT-3)
จึงเป็น MoSCoW = Could — ส่วน REQ-18 (กลไกยืนยันตัวตนก่อนจับคู่อุปกรณ์) แม้เป็น Could เช่นกัน (เพราะมีอยู่เพื่อ
รองรับ INT-2/INT-3 เท่านั้น ไม่มี feature อื่นที่เป็น Must/Should พึ่งพา) แต่เป็น **precondition ทางเทคนิคร่วม**
ที่ INT-2/INT-3 ทั้งคู่ต้องผ่านก่อนจึงจะทำงานได้จริงบนมือถือ (companion app ไม่มีหน้าจอ auth ของตัวเอง — ดู
[Onboarding spec § ONB-0](20260823-01-onboarding-personalization.md#ข้อสมมติฐานการตัดสินใจที่ยืนยันแล้ว))

## เงื่อนไข/กติกาทางธุรกิจ (Business Rules)

1. **REQ-11**: คำนวณวันที่คาดว่าจะถึงน้ำหนักเป้าหมาย จากอัตราขาดดุลแคลอรี่เฉลี่ยที่บันทึกจริง
2. **REQ-12**: ซิงค์น้ำหนัก/องค์ประกอบร่างกายจากตาชั่งอัจฉริยะผ่าน Bluetooth หรือ Health API
3. **REQ-13**: ดึงแคลอรี่เผาผลาญจริงจาก Apple Health/Google Health Connect มาทดแทนค่าที่ระบบประมาณจากวิดีโอ
4. **REQ-18** (ใหม่ 2026-08-30): การยืนยันตัวตนก่อนจับคู่อุปกรณ์ผ่านรหัสจับคู่ (Pairing Code) — ผู้ใช้ที่
   ล็อกอินอยู่บนเว็บแอปแล้ว (ONB-0) ขอรหัสจับคู่อุปกรณ์แบบตัวเลข 6 หลักจากหน้าโปรไฟล์ ระบบ (server) เป็น
   ผู้สร้างรหัสนี้ผูกกับบัญชีผู้ใช้ที่ล็อกอินอยู่ขณะนั้นเสมอ รหัสมีอายุการใช้งาน **5 นาที** และเป็น
   **single-use** (ใช้ซ้ำไม่ได้หลัง redeem สำเร็จหรือหมดอายุ) ผู้ใช้กรอกรหัสนี้บน companion mobile app
   เพื่อแลกเป็น session ที่ authenticated แบบ silent (sign in โดยไม่ต้องกรอก credential ซ้ำ) ผูกกับบัญชี
   เดิมที่สร้างรหัสไว้ ก่อนเข้าสู่หน้าจับคู่อุปกรณ์จริง (INT-2/INT-3)

## Acceptance Criteria

- [ ] ผู้ใช้เห็นวันที่คาดว่าจะถึงน้ำหนักเป้าหมาย คำนวณจากอัตราขาดดุลแคลอรี่เฉลี่ยที่บันทึกจริง (REQ-11)
- [ ] น้ำหนัก/องค์ประกอบร่างกายซิงค์จากตาชั่งอัจฉริยะเข้าโปรไฟล์อัตโนมัติ (REQ-12)
- [ ] เมื่อมีข้อมูลจาก wearable ระบบใช้แคลอรี่เผาผลาญจริงจาก wearable แทนค่าประมาณจากวิดีโอ (REQ-13)
- [ ] ผู้ใช้ขอรหัสจับคู่อุปกรณ์ 6 หลักจากเว็บ แล้วกรอกบนมือถือเพื่อยืนยันตัวตนแบบ silent ก่อนเข้าหน้าจับคู่
      อุปกรณ์จริงได้สำเร็จ และรหัสหมดอายุ/ใช้ซ้ำไม่ได้ตามกติกาที่กำหนด (REQ-18)

ดูรายละเอียดแบบ Given-When-Then เต็มรูปแบบที่ [acceptance-criteria.md](../acceptance-criteria.md)

## ข้อสมมติฐาน/การตัดสินใจที่ยืนยันแล้ว

ค่าคงที่ 7,700 kcal ≈ 1 กก. ไขมัน ที่ REQ-11 ต้องใช้ถูก resolve ไว้แล้วใน
[Onboarding/ONB-3 (REQ-02)](20260823-01-onboarding-personalization.md#ข้อสมมติฐานการตัดสินใจที่ยืนยันแล้ว)

- **กลไกระบุตัวตนผู้ใช้บนมือถือก่อนจับคู่อุปกรณ์ (pairing-code) เป็น REQ-18 แยกต่างหาก พร้อม Feature ID
  ของตัวเอง (INT-0) — ยืนยันกับผู้ใช้งานแล้ว 2026-08-30**: เดิมบันทึกไว้เป็น "จุดที่ยังไม่ได้ระบุ" ว่าควรมี
  REQ number ของตัวเองหรือไม่ (ดู codebase 2026-08-30) ผู้ใช้งานยืนยันให้ (ก) ตั้งเป็น **REQ-18** ใหม่
  (ดู "เงื่อนไข/กติกาทางธุรกิจ" ด้านบน) และ (ข) ให้ Feature ID ของตัวเอง คือ **INT-0** ผูกกับ Epic Smart
  Integrations (ไม่ใช่ Onboarding) — โดยตั้งชื่อ/จัดวางตามแบบแผนเดียวกับที่ **ONB-0** เคยได้รับ Feature ID
  ของตัวเองมาก่อนแล้ว ในฐานะ foundational precondition ที่ feature อื่นในกลุ่มเดียวกันใช้ร่วมกัน (ONB-0 เป็น
  precondition ของทั้งแอป; INT-0 เป็น precondition เฉพาะของ INT-2/INT-3 เท่านั้น) เหตุผลที่ผูกกับ Smart
  Integrations แทน Onboarding: กลไกนี้เกิดขึ้นเฉพาะตอนผู้ใช้ต้องการจับคู่อุปกรณ์ (INT-2/INT-3) เท่านั้น
  ไม่ใช่ส่วนหนึ่งของ flow onboarding บนเว็บที่ ONB-0/1/2/3 ครอบคลุมอยู่แล้ว

  กลไกที่ implement จริงในโค้ดมีดังนี้ (อ้างอิงเดิมจาก codebase 2026-08-30):
  1. ผู้ใช้ที่ล็อกอินอยู่แล้วบนเว็บแอป (จาก ONB-0) เปิดหน้าโปรไฟล์ กดขอรหัสจับคู่อุปกรณ์ → server สร้างรหัส
     จับคู่ 6 หลัก อายุการใช้งาน 5 นาที แสดงบนหน้าจอเว็บ
  2. ผู้ใช้เปิด companion app บนมือถือ กรอกรหัส 6 หลักนั้น → server ตรวจสอบรหัส (ถูกต้อง/ยังไม่หมดอายุ/
     ยังไม่ถูกใช้ — single-use) แล้ว mint short-lived token ผูกกับบัญชีผู้ใช้เดิมที่สร้างรหัสไว้
  3. มือถือใช้ token นั้นเข้าสู่ระบบแบบ silent (ไม่ต้องกรอกรหัสผ่านซ้ำ) แล้วเข้าสู่หน้าจับคู่อุปกรณ์จริง
     (INT-2/INT-3 UI)

  REQ-18/INT-0 เป็น **precondition ทางเทคนิคร่วม** ของ INT-2 และ INT-3 ทั้งคู่ ไม่ใช่ส่วนหนึ่งของเนื้อหา
  business rule ของ REQ-12/REQ-13 เอง (ซึ่งยังคงเนื้อหาเดิมไม่เปลี่ยนแปลง) — ในเอกสาร
  [user-journeys.md](../../02-design/01-prototypes/user-journeys.md) ขั้นตอนเหล่านี้ถูกแยกเป็น entry ของ
  ตัวเอง (INT-0) แล้ว โดย INT-2/INT-3 อ้างอิงกลับมาเป็น precondition แทนการ duplicate ขั้นตอนซ้ำเหมือนก่อน
  หน้านี้

## จุดที่ยังไม่ได้ระบุ / ควรยืนยันเพิ่มเติม

- **INT-1 (REQ-11)**: ไม่ได้ระบุจำนวนวัน log ขั้นต่ำก่อนเริ่มพยากรณ์ได้
- **INT-2/INT-3 (REQ-12, REQ-13)**: ไม่ได้ระบุลำดับความสำคัญเมื่อมีข้อมูลชนกัน (เช่น ชั่งน้ำหนักหลายครั้ง
  ต่อวันจากตาชั่งอัจฉริยะ ควรใช้ค่าล่าสุดหรือค่าเฉลี่ย หรือค่าจาก wearable ต่างจากค่าประมาณจากสูตร MET
  มากควรจัดการอย่างไร)
- **INT-0 (REQ-18, ใหม่ 2026-08-30)**: ยังไม่ได้ระบุกติกา rate limiting เมื่อผู้ใช้กรอกรหัสจับคู่ผิดซ้ำ ๆ
  หลายครั้งติดกันบนมือถือ (เช่น ควร lock ชั่วคราวหลังกี่ครั้ง) — เป็นรายละเอียด implementation ปลีกย่อยที่
  ไม่กระทบโครงสร้าง journey ของ feature ระดับ Must/Should เพราะ INT-0 เองเป็น Could-priority
