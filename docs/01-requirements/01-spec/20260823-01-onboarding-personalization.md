# 20260823-01 - Onboarding & Personalization

- **ประเภท:** Feature
- **สถานะเอกสาร:** Ready
- **วันที่สร้าง:** 2026-08-23

## ขอบเขต (Scope)

**อยู่ในขอบเขต (In scope)**

- ผู้ใช้สมัครสมาชิก เข้าสู่ระบบ ลืมรหัสผ่าน และออกจากระบบ (ยืนยันจากผู้ใช้งาน 2026-08-29 — ดู "ข้อสมมติฐาน/
  การตัดสินใจที่ยืนยันแล้ว")
- ผู้ใช้ใหม่กรอกข้อมูลร่างกาย (อายุ เพศ น้ำหนัก ส่วนสูง ระดับกิจกรรม) เพื่อคำนวณ BMR/TDEE
- ผู้ใช้เลือกอุปกรณ์ที่มี (ไม่มีอุปกรณ์ / ดัมเบล / ยิมครบชุด) เพื่อกรองวิดีโอที่แนะนำได้จริง
- ผู้ใช้ตั้งเป้าหมายหลัก (ลดน้ำหนัก / กระชับสัดส่วน / เพิ่มความอึด) แล้วระบบแปลงเป็นค่าแคลอรี่เป้าหมายรายวัน

**นอกขอบเขต (Out of scope)**

- Multi-factor authentication (MFA) — ไม่ได้ระบุว่าจำเป็นสำหรับแอปนี้ ไม่อยู่ในขอบเขตรอบนี้
- Social login provider อื่นนอกเหนือจาก Google/Apple (เช่น Facebook, LINE) — ยึดตามที่ `tech-stack.md`
  เลือกไว้แล้วเท่านั้น (email/password, Google OAuth, Sign in with Apple)
- การจัดการหลายบัญชี/สลับบัญชีบนอุปกรณ์เดียว (account switching) — ยังไม่ได้ระบุไว้
- ยังไม่ได้ระบุไว้ในเอกสารต้นฉบับอื่น (product backlog เดิม) — ถ้ามีขอบเขตที่ต้องการตัดออกเพิ่มเติมอย่างชัดเจน
  ให้ระบุเพิ่มก่อนเข้าสู่ 02-design

## รายละเอียด (Description)

Onboarding เป็นขั้นตอนแรกที่ผู้ใช้ใหม่ทุกคนต้องผ่านก่อนใช้งานฟีเจอร์อื่น ผลลัพธ์จากขั้นตอนนี้ (TDEE,
โปรไฟล์อุปกรณ์, เป้าหมายแคลอรี่รายวัน) เป็น input ที่ [Daily YouTube Recommendation](20260823-02-daily-youtube-recommendation.md)
และ [Planner & Logging](20260823-03-planner-logging.md) ต้องใช้ต่อ

**เพิ่มเติม 2026-08-29**: ก่อนหน้านี้เอกสารนี้ (และทั้ง backlog) ยังไม่มี Feature ใดครอบคลุมเรื่อง Login/
บัญชีผู้ใช้เลย — มีแค่ `tech-stack.md` ที่เลือก Firebase Authentication ไว้ล่วงหน้าเป็นข้อสมมติฐานทาง
เทคนิค (และ NFR-04/06/11 อ้างถึง "เมื่อมีระบบบัญชีผู้ใช้จริง" เป็นเงื่อนไขในอนาคต) ผู้ใช้งานยืนยันให้เพิ่ม
Authentication เป็น requirement จริงในเอกสารนี้ (รวมเข้า Epic Onboarding & Personalization เดิม แทนที่จะ
แยก epic ใหม่) เพราะ login/สมัครสมาชิกเป็น step แรกสุดที่เกิดก่อนกรอกข้อมูลส่วนตัว (REQ-01) ในทาง product
flow เดียวกัน — ผลลัพธ์จาก Authentication (บัญชีผู้ใช้/`userId`) เป็น precondition ของทุก REQ อื่นในเอกสาร
นี้และทุก epic อื่นในโปรเจกต์ ไม่ใช่แค่ input ทางเดียวแบบ REQ-01/02/03

## เงื่อนไข/กติกาทางธุรกิจ (Business Rules)

1. **REQ-01**: คำนวณ BMR/TDEE จากอายุ เพศ น้ำหนัก ส่วนสูง ระดับกิจกรรม (เช่น สูตร Mifflin-St Jeor)
2. **REQ-02**: แปลงเป้าหมาย (ลด/กระชับ/เพิ่มความอึด) เป็นค่าส่วนต่างแคลอรี่ (deficit/surplus) ต่อวัน
3. **REQ-03**: บันทึกโปรไฟล์อุปกรณ์ผู้ใช้ และใช้เป็นตัวกรองวิดีโอที่แนะนำ
4. **REQ-14** (ใหม่ 2026-08-29): ผู้ใช้สมัครสมาชิก (Sign-up) ได้ 3 วิธี — email/password, Google OAuth,
   Sign in with Apple (ตามที่ `tech-stack.md` เลือก Firebase Authentication ไว้) ระบบต้องสร้างบัญชีผู้ใช้
   ใหม่ (`userId`) ก่อนเข้าสู่ขั้นตอน REQ-01 เสมอ — ห้ามเริ่มกรอกข้อมูลส่วนตัวก่อนมีบัญชีผู้ใช้จริง
5. **REQ-15** (ใหม่ 2026-08-29): ผู้ใช้เข้าสู่ระบบ (Login) ได้ด้วยวิธีเดียวกับที่สมัครไว้ (email/password,
   Google, หรือ Apple) ระบบต้องจดจำสถานะเข้าสู่ระบบไว้ (session persistence) เพื่อไม่ต้อง login ซ้ำทุกครั้ง
   ที่เปิดแอป จนกว่าผู้ใช้จะออกจากระบบเอง (REQ-17) หรือ session หมดอายุ
6. **REQ-16** (ใหม่ 2026-08-29): ผู้ใช้ที่สมัครด้วย email/password และลืมรหัสผ่าน ต้องขอรีเซ็ตรหัสผ่านผ่าน
   อีเมลที่ลงทะเบียนไว้ได้ (ไม่ใช้กับบัญชีที่สมัครผ่าน Google/Apple เพราะไม่มีรหัสผ่านให้รีเซ็ต)
7. **REQ-17** (ใหม่ 2026-08-29): ผู้ใช้ออกจากระบบ (Logout) ได้ทุกเมื่อจากหน้าโปรไฟล์ ระบบต้องล้าง session
   ที่จดจำไว้ตาม REQ-15 ทันที

## Acceptance Criteria

- [ ] ผู้ใช้สมัครสมาชิกได้ด้วย email/password, Google, หรือ Apple ก่อนเริ่ม onboarding กรอกข้อมูลส่วนตัว
      (REQ-14)
- [ ] ผู้ใช้เข้าสู่ระบบได้ด้วยวิธีเดียวกับที่สมัครไว้ และแอปจดจำสถานะ login ไว้จนกว่าจะออกจากระบบ (REQ-15)
- [ ] ผู้ใช้ที่สมัครด้วย email/password ขอรีเซ็ตรหัสผ่านผ่านอีเมลได้ (REQ-16)
- [ ] ผู้ใช้ออกจากระบบได้จากหน้าโปรไฟล์ และ session ถูกล้างทันที (REQ-17)
- [ ] ผู้ใช้กรอกอายุ เพศ น้ำหนัก ส่วนสูง ระดับกิจกรรม แล้วระบบคำนวณ TDEE ให้อัตโนมัติ (REQ-01)
- [ ] ผู้ใช้เลือกอุปกรณ์ที่มีได้ และค่านี้ถูกใช้กรองวิดีโอที่แนะนำในทุก session ถัดไป (REQ-03)
- [ ] ผู้ใช้เลือกเป้าหมายหลักได้ 1 ใน 3 แบบ และระบบแปลงเป็นค่าแคลอรี่เป้าหมายรายวันที่เจาะจง (REQ-02)

ดูรายละเอียดแบบ Given-When-Then เต็มรูปแบบที่ [acceptance-criteria.md](../acceptance-criteria.md)

## ข้อสมมติฐาน/การตัดสินใจที่ยืนยันแล้ว

ยืนยันกับผู้ใช้งานแล้วเมื่อ 2026-08-23 (ผ่าน audit ของ skill `feature-list-journey`, ดูรายละเอียดเต็มใน
[User Journey ของ ONB-3](../../02-design/01-prototypes/user-journeys.md#onb-3--ตั้งเป้าหมายหลัก-req-02)):

- **ค่า deficit/surplus ต่อวัน (REQ-02)**: ใช้ค่าคงที่ตายตัวต่อเป้าหมาย — ลดน้ำหนัก = TDEE − 500 kcal/วัน,
  กระชับสัดส่วน = TDEE + 0 kcal/วัน (maintenance), เพิ่มความอึด = TDEE + 300 kcal/วัน — พร้อม safety floor
  ห้ามต่ำกว่า 1,200–1,500 kcal/วัน (ใช้ค่าคงที่ 7,700 kcal ≈ 1 กก. ไขมัน ร่วมกับ Smart Integrations/INT-1)
- **การเลือกอุปกรณ์แบบ multi-select (REQ-03)**: backfill เข้าเอกสารนี้จาก full consistency audit ของ skill
  `feature-list-journey` วันที่ 2026-08-27 — ไม่ใช่ ask-user round ใหม่ แต่เป็นการยืนยัน "spec ตามหลัง"
  (reverse-drift ที่ไม่ขัดแย้งกับสิ่งใด): `user-journeys.md#onb-2` ระบุอยู่แล้วว่า "เลือกได้มากกว่า 1
  ถ้าจำเป็น" และ prototype `v1/02-onboarding-equipment.html` กับ test case `TC-ONB-2-002` ก็ implement/ทดสอบ
  ตามนั้นสอดคล้องกันทั้งคู่อยู่แล้วก่อน audit นี้ — จึงยืนยันเป็นทางการว่า **ผู้ใช้เลือกอุปกรณ์ได้มากกว่า 1
  ประเภทพร้อมกัน** (เช่น ดัมเบล + ยิมครบชุด) ไม่ใช่ single-select ส่วนกติกา mutual-exclusion ระหว่าง
  "ไม่มีอุปกรณ์" กับอุปกรณ์เฉพาะเจาะจง (เลือกพร้อมกันไม่ได้) ยังคงเป็นการตัดสินใจของ prototype เท่านั้น
  ไม่ใช่ข้อกำหนดที่ resolve ในเอกสารนี้
- **ช่องกรอกน้ำหนักเป้าหมาย (target weight) ใน ONB-3/REQ-02**: ยืนยันกับผู้ใช้งานแล้วเมื่อ 2026-08-28
  (ถามผ่าน AskUserQuestion โดย `architecture-builder` ระหว่างเตรียม High-Level Architecture — เลือก
  **ตัวเลือก (A) เพิ่มช่องกรอกน้ำหนักเป้าหมายใน ONB-3**) — gap ที่พบ: `user-journeys.md`'s INT-1 ระบุ
  precondition ว่า "มีเป้าหมายน้ำหนัก (จาก ONB-3)" แต่ ONB-3 เดิมให้ผู้ใช้เลือกแค่ **ประเภทเป้าหมาย**
  (ลดน้ำหนัก/กระชับสัดส่วน/เพิ่มความอึด) แล้วแปลงเป็นค่า kcal offset เท่านั้น ไม่มีขั้นตอนกรอกตัวเลขน้ำหนัก
  เป้าหมายจริงเลย ซึ่ง INT-1 (พยากรณ์วันถึงเป้าหมายน้ำหนัก) ต้องใช้ค่านี้จริงในการคำนวณ — เพิ่มขั้นตอนใน
  ONB-3 ดังนี้:
  - เมื่อผู้ใช้เลือกเป้าหมาย **"ลดน้ำหนัก"**: ระบบให้กรอกตัวเลขน้ำหนักเป้าหมาย (target weight, kg)
    เป็น **ช่องบังคับ (mandatory)** เพราะเป็นกรณีเดียวที่เป้าหมายผูกกับตัวเลขน้ำหนักโดยตรงและเป็นกรณีที่
    INT-1 ต้องใช้จริง
  - เมื่อผู้ใช้เลือกเป้าหมาย **"กระชับสัดส่วน"** หรือ **"เพิ่มความอึด"**: ช่องกรอกน้ำหนักเป้าหมายเป็น
    **ทางเลือก (non-mandatory)** — ดุลยพินิจของ `feature-list-journey` เพราะเป้าหมายทั้งสองแบบนี้ไม่ได้
    นิยามด้วยตัวเลขน้ำหนักโดยตรง (maintenance/เพิ่มความอึดไม่จำเป็นต้องมีเป้าหมายน้ำหนักที่ชัดเจน) ถ้าผู้ใช้
    ข้ามช่องนี้ INT-1 จะยังใช้งานไม่ได้สำหรับผู้ใช้คนนั้นจนกว่าจะกรอกภายหลัง (ดู Alt/Edge Case ของ INT-1
    ที่ปรับตาม)
  - ค่านี้ถูกบันทึกลงโปรไฟล์ผู้ใช้พร้อมกับเป้าหมายแคลอรี่รายวัน และเป็นแหล่งที่มาจริงของ precondition
    "มีเป้าหมายน้ำหนัก" ที่ [INT-1](../../02-design/01-prototypes/user-journeys.md#int-1--พยากรณ์วันถึงเป้าหมายน้ำหนัก-req-11)
    ใช้อ้างอิง (แก้ไขให้ตรงกันแล้วในเอกสารนั้น)

- **Authentication เป็น requirement ใหม่ (ยืนยันจากผู้ใช้งาน 2026-08-29 ผ่าน AskUserQuestion)**: ก่อนหน้านี้
  ทั้ง backlog ไม่มี Feature ใดครอบคลุมเรื่อง Login/บัญชีผู้ใช้เลย มีแค่ `tech-stack.md` ที่เลือก Firebase
  Authentication ไว้ล่วงหน้าเป็นข้อสมมติฐานทางเทคนิค ผู้ใช้งานยืนยัน 3 ประเด็น:
  1. **Epic placement**: รวมเข้า Epic Onboarding & Personalization เดิม (ไม่แยก epic ใหม่) เพราะ
     login/สมัครสมาชิกเป็น step แรกสุดของ flow เดียวกันกับ ONB-1/2/3
  2. **ขอบเขต**: ครบวงจร — สมัครสมาชิก (REQ-14) + เข้าสู่ระบบ (REQ-15) + ลืมรหัสผ่าน (REQ-16) +
     ออกจากระบบ (REQ-17) ไม่ใช่แค่ Login/Sign-up อย่างเดียว
  3. **วิธี Authentication**: ครบทั้ง 3 วิธีตามที่ `tech-stack.md` เลือกไว้แล้ว — email/password, Google
     OAuth, Sign in with Apple — ไม่ลด scope เหลือแค่ email/password

## จุดที่ยังไม่ได้ระบุ / ควรยืนยันเพิ่มเติม

- **ONB-3 (REQ-02)**: กรณีผู้ใช้เลือกเป้าหมาย "กระชับสัดส่วน"/"เพิ่มความอึด" แล้วข้ามช่องน้ำหนักเป้าหมาย
  (non-mandatory) — ยังไม่ได้ระบุว่าระบบควรเตือน/แนะนำให้กรอกภายหลังผ่านช่องทางไหน (เช่น banner ใน
  หน้า Progress/Insights) หรือปล่อยให้ INT-1 แสดง empty state เฉยๆ จนกว่าผู้ใช้จะกรอกเอง
- **REQ-14 (สมัครสมาชิก)**: ยังไม่ได้ระบุว่าต้องมีขั้นตอนยืนยันอีเมล (email verification) ก่อนใช้งานได้จริง
  หรือไม่ — ถ้าต้องมี จะกระทบ flow ว่าเข้าสู่ REQ-01 ได้ทันทีหลังสมัคร หรือต้องรอยืนยันอีเมลก่อน
- **REQ-14 (สมัครสมาชิก)**: ยังไม่ได้ระบุกติกาความซับซ้อนของรหัสผ่าน (password policy) สำหรับ email/
  password — ต้องยืนยันก่อน implement จริง
- **REQ-15 (เข้าสู่ระบบ)**: ยังไม่ได้ระบุระยะเวลาหมดอายุของ session (session timeout) ที่แน่นอน
- **ความสัมพันธ์กับ NFR-04/06/11**: NFR doc เดิมอ้างถึง "เมื่อมีระบบบัญชีผู้ใช้จริง" เป็นเงื่อนไขในอนาคต —
  ตอนนี้ REQ-14–17 ทำให้เงื่อนไขนั้นเป็นจริงแล้ว NFR-04 (เข้ารหัส)/NFR-06 (สิทธิ์ลบข้อมูล)/NFR-11 (PDPA)
  ควรถูก audit อีกครั้งว่าเนื้อหายังครบถ้วนสำหรับระบบบัญชีผู้ใช้จริงหรือไม่ (ไม่ใช่แค่สมมติฐานอนาคตอีกต่อไป)
  — เป็นงานของ skill ที่เกี่ยวข้อง ไม่ใช่ตัดสินใจในเอกสารนี้

## ความสัมพันธ์กับเอกสารอื่น (Requirement Cross-reference Analysis)

Onboarding เป็นเอกสาร requirement ต้นทางของทั้งโปรเจกต์ — ผลลัพธ์ (TDEE, โปรไฟล์อุปกรณ์, เป้าหมายแคลอรี่รายวัน)
ถูกใช้เป็น input โดยตรงใน [Daily YouTube Recommendation](20260823-02-daily-youtube-recommendation.md) (REC-1, REC-2)
และค่าคงที่ 7,700 kcal/kg ที่ resolve ในเอกสารนี้ถูกใช้ร่วมกับ Smart Integrations (INT-1) ด้วย REQ-14–17
(Authentication) เป็น precondition ของทุก REQ อื่นในโปรเจกต์ทั้งหมด (ไม่ใช่แค่ epic นี้) เพราะทุก REQ
ต้องมี `userId` จริงก่อนบันทึกข้อมูลใดๆ — ผูกกับ [tech-stack.md](../../02-design/02-technical/tech-stack.md)
ที่เลือก Firebase Authentication ไว้ล่วงหน้าแล้ว (email/password + Google OAuth + Sign in with Apple) และ
[NFR-04/NFR-06/NFR-11](20260827-05-non-functional-requirements.md) ที่อ้างถึงระบบบัญชีผู้ใช้เป็นเงื่อนไข
